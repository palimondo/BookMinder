# The BDD/TDD Style BookMinder Aims For — Reconstructed From Git Replay

Method: replay of all 117 Python-touching commits (`git log --reverse -- '*.py'`), from `9e7bd38` (first implementation, 2025-04-13) to `0bf00d1` (last product commit, 2025-07-21), reading key diffs and commit bodies. Every rule below is stated with its recovered motivation; where the history is a correction (revert, deletion, redo), the correction is treated as the author teaching the principle. Where motivation could not be recovered, that is said explicitly.

---

## 1. Spec style rules

**1.1 Specs are the requirements document, so they must read as sentences.** `pytest.ini` discovers `*_spec.py` / `describe_*` / `it_*`, and `pytest --spec` renders the suite as living documentation. Naming flows from the story card: story `filter-by-cloud-status.yaml` → `describe_bookminder_list_with_filter` → `it_filters_by_cloud_status` (`7060287`, codified `3db7e5a`). Motivation: prose documentation rots (this repo's README still advertises unbuilt features), but a spec that stops describing reality fails. The spec tree is the only description of the system that is mechanically forced to stay true.

**1.2 One `describe_` per public function or command; one `it_` per observable behavior; no ceremonial nesting.** Taught by `3d8bc5b`, which flattened `describe_book_library / describe_when_listing_books` (the AI's initial RSpec-cargo-cult shape from `9e7bd38`) into `describe_list_books`, `describe_find_book_by_title`, `describe_list_recent_books`. Motivation: when the unit of behavior is a function, the function name already *is* the context; an extra "when" layer adds indentation without adding meaning, and the `--spec` output reads worse, not better.

**1.3 Docstrings are for pending specs only.** A skipped spec carries the story's Gherkin as its docstring — `7060287` commits `it_shows_only_local_books_when_flag_is_local` as `@pytest.mark.skip(reason="Implementation pending")` with the full `when:/then:` block and `pass` as its body; `20b03dc` later enables such a test when its fixture is ready. Once implemented, the docstring is deleted (`3d8bc5b`, `48596a6`, `f3d57b3`, `6f786cc`) because the test name plus assertions now *are* the specification, and a docstring restating them is a second copy that can drift. The skip marker is also the mechanism that lets the committed suite stay green while unfinished scenarios remain visible in `--spec` output as backlog.

**1.4 Assertion strength is layer-dependent, and always as strong as the layer allows.**
- Unit specs on pure functions assert **exact equality of the entire output**: `assert result == "Test Book - Test Author (42%) • Sample ☁️"` (`2859fad`), built up with progressive complexity (no attributes → progress → sample → cloud → all → ordering property). Motivation: a pure function's contract is its whole output; substring checks would let format regressions ship. Where the property is relational (ordering of indicators), the spec asserts the relation directly: `result.index("• Sample") < result.index("☁️")` (`2859fad`, added with the bug-fix `e72007f`).
- Integration specs assert **named inhabitants of a curated fixture and exact sets**: `assert sample_titles == expected_samples` with `{"Snow Crash", "Tiny Experiments", "What's Our Problem?"}` (`22e1378`, `library_containers_spec.py`). Motivation: the fixture census is known, so anything weaker throws information away — and a universally-quantified assertion (`for book in books: assert ...`) passes vacuously on an empty result, so it is paired with `assert len(books) > 0` whenever non-emptiness is part of the claim (`5730bf4`, `b246d7b`'s integration half).
- Acceptance specs assert **the conversation, not the prose**: `mock_list.assert_called_once_with(user=None, filter='cloud')` plus `format` call order (`552a9a3`). Motivation stated in that commit body: the CLI's responsibility is coordination; asserting output strings couples the CLI spec to formatting details already covered by the formatting unit specs, so a format change would break two suites for one behavior.
- Error-path specs assert **which specific path fired**: distinguish "BKLibrary directory not found:" from "No BKLibrary database found in:" (`e65c8b6`). Motivation is a scar: `it_handles_user_who_never_opened_apple_books` was green for ~ten days because an *untracked* fixture directory made a generic raises-check pass for the wrong reason; the commit body says the specific-message assertion "would have caught this issue immediately." A test that can pass for the wrong reason is not a specification.
- Every non-obvious assertion carries a diagnostic message interpolating the counterexample: `f"Expected cloud book: {book['title']}"`, `f"Command failed: {result.stderr}"`. Motivation: a failing spec should hand you the falsifying datum, not just a boolean.

**1.5 Test data is minimal and its realism signals intent.** Collaboration tests use two abstract books `B1/A1`, `B2/A2` — the 0-1-many pattern, "minimal data (2 books)" (`552a9a3`) — because there the data is a token, and realistic titles would falsely suggest the content matters. Integration tests use real titles ("Extreme Programming Explained", "Lao Tzu: Tao Te Ching") because there the data *is* the point: it is the actual census of the fixture database. Stubbing not asserted upon is deleted: `94e2af6` removes `mock_list_recent.return_value = []` from passthrough tests because "the default MagicMock is sufficient" — every line of setup must be load-bearing, since unused stubbing implies the test cares about something it never checks.

**1.6 Four layers with definitional (not preferential) mock rules** (`be394a0`…`0bf00d1`; contracts written into each layer's `__init__.py` by `7dfe126`):
- `specs/unit/` — pure logic, zero I/O; stubs/mocks for anything external. `row_stub(**overrides)` builds a minimal `sqlite3.Row` dict with defaults so each spec states only the fields it is about (`e72007f`).
- `specs/integration/` — **real fixtures, no mocks, ever.** This is not a preference: an integration test exists to exercise the real collaborator (the SQLite file, the plist, the container layout). Mocking it would verify your own stub — the test would be a tautology. Edge cases with real broken resources (corrupt DB, missing container) live here (`30c2fe5`).
- `specs/acceptance/` — `CliRunner` plus mocks of the library functions the CLI *owns the interface to*. This is the London-school boundary: mock roles/protocols you own at an architectural seam, and specify the conversation across it (`552a9a3`: "GOOS principles of testing at architectural boundaries").
- `specs/e2e/` — **exactly one** subprocess test of the whole stack. The `__init__` says it: "Be minimal — we only need ONE test to verify wiring." Motivation recovered from `82d3990`: converting all CLI tests to `CliRunner` (`1880103`) silently removed the only coverage of the `__main__.py` entry point, so the subprocess revert established the "one true end-to-end test" — its subject is *wiring*, which no in-process test can reach, and one is enough because a second would merely re-test behavior slowly.

**1.7 Fixtures enter through the front door.** The `--user` parameter (`3103e4d`) doubles as the seam: tests pass a synthetic `$HOME` (`fixtures/users/test_reader`, `never_opened_user`, `fresh_books_user`, `legacy_books_user`, `corrupted_db_user`) whose directory trees replicate Apple's real container layout byte-for-path. `8e632f6` deleted the `monkeypatch` of `_books_plist` in favor of this: "This allows us to test the real code paths… No more monkeypatching needed." Motivation: patching a private function couples the spec to an implementation name and *bypasses the path-construction code you claim to test*; a real path through real directories tests it. Each per-scenario user home encodes one environmental hypothesis (never opened / fresh / legacy / corrupted), making the fixture directory itself a readable catalogue of the edge cases the product handles (`0dd8aa0`, `30c2fe5`).

**1.8 Patch a constant with nonsense to prove ignorance.** `1d1fb34` patches `SUPPORTED_FILTERS` to `{'foo', 'bar'}` and rejects `'baz'`: "mock filter names… to prove that the CLI completely delegates filter knowledge to the library." Motivation: asserting with *real* filter names could pass even if the CLI had its own hardcoded list; nonsense values make the property — the CLI knows nothing about filters — falsifiable. (Note how the lapse then subverted exactly this — §4.)

**1.9 Symmetry is expressed as a table.** `9cac7d7` collapses 8 near-identical filter tests into one doubly-parameterized test over (command × filter). Motivation from its body: the CLI is a uniform passthrough, and a table-shaped spec makes any asymmetry — a filter handled specially in the CLI — a visible anomaly rather than a buried inconsistency. This is the "Consistency Trumps Cleverness" repair for the YOLO-era style mixing.

**1.10 What a spec must never do** — each rule bought with a deletion:
- Never test the *absence of a problem*. `d8b5722` removes `it_attempts_to_read_from_bklibrary_database` (asserting output ≠ three hardcoded titles): it "tested the absence of a problem rather than presence of correct behavior," was environment-fragile, and existed only to force out a fake. The stated correct move: tolerate the RED acceptance test while driving the real implementation through unit specs — the RED state itself is the pressure; a meta-test is a crutch that outlives its purpose as suite noise.
- Never assert about data you never injected. `b246d7b`'s CLI test asserts `"Sample Book" not in result.output` while the mock returns only a regular book — an assertion that cannot fail, i.e. fake strength. (Identified in the retrospective; repaired by `9cac7d7`/`677a251`.)
- Never depend on the developer's real environment. The original `9e7bd38` specs read the author's actual library; three commits (`2d331e9`, `48ac46e`, `147f59f`) were needed to make CI pass, teaching: a spec that only passes on one machine specifies that machine, not the product.

## 2. Implementation style qualities

**2.1 Code is a liability; deletion is the preferred fix.** `e7a5fa4` is the constitutive example: an untested `os.path.exists` guard (present since `9e7bd38`) silently excluded valid books whose EPUBs weren't downloaded from iCloud. The fix *removed* the guard and the blanket `except Exception`, "removing implementation that lacked tests rather than adding tests retroactively" — reaching 100% coverage *by subtraction*. Motivation: an untested branch is unverified behavior that can be wrong invisibly; retrofitting tests would ratify code no requirement asked for. Same principle re-applied in `b73a618` (error handling removed because no acceptance criterion demanded it — note the replacement is a loud `assert BKLIBRARY_DB_FILE is not None`, making the assumption crash-visible instead of silently handled) and `c851f95` (NULL-check removed "after verifying that ZISSAMPLE values in our test fixtures are always 0 or 1" — defensive code needs demonstrated requirements, and the demonstration is checked evidence, not imagination).

**2.2 Error handling exists only once a story demands it, and then it is specific.** `0dd8aa0` introduces `BookminderError` and catches exactly `FileNotFoundError` and `sqlite3.Error`, re-raised with the offending path in the message — driven by the `handle-user-environments` story, one fixture per scenario. The CLI's whole error policy is one boundary catch of the domain type, echoing the message with no traceback, and the acceptance layer specifies precisely that contract without coupling to message text (`cb47cac`: "verifies behavior at the architectural boundary rather than testing specific error messages, making it resilient to implementation changes"). Speculative widenings get reverted wholesale (`6769f2f` → `1b07bd5`).

**2.3 YAGNI operationalized as testability.** `3d8bc5b` removes `sort_by` with the reason "YAGNI and untestable with single book": a capability the current fixtures cannot falsify is not a feature, it is speculation with a keyword argument. `bcb5223` reverts the `LibraryPaths` dataclass: structure introduced ahead of a second use is a bet the author declines to carry. Motivation-in-common: everything present must be exercised by a spec *now*, so the coverage report doubles as a YAGNI detector.

**2.4 Minimal GREEN, honest fake.** The walking skeleton (`eca50d2`) commits three hardcoded `click.echo` lines and *says so* ("Minimal hardcoded implementation to establish walking skeleton") behind a real subprocess acceptance test; `fa0bc72` commits `SUPPORTED_FILTERS = {"dummy"}` labeled "just enough to make the test green." Motivation: the fake proves the pipeline end-to-end; the still-RED (or newly-specific) test carries the unfinishedness. The fake is removed by *driving real behavior through unit specs*, never by a spec that detects the fake (§1.10).

**2.5 Functional core, imperative shell.** Pure functions are extracted precisely when a property needs cheap specification: `format`/`format_book_list` extracted so output shaping is unit-testable without subprocess (`74e6220` → `2859fad`); `_build_books_query` split from `_query_books` so the column census is testable without I/O — "prevents accidental removal of columns that would break sample detection" (`10048e1`). I/O is confined to `_query_books`/`_read_books_plist`. Knowledge lives in one layer: path resolution moved CLI→library (`5a50925` "to the library where it belongs"), filter vocabulary exported by the library (`SUPPORTED_FILTERS`) so the CLI validates without owning the list. Duplication is eliminated promptly after the second occurrence, not before (`24dc928` after `list all` landed).

**2.6 Typing and idiom.** `Book` is a `TypedDict` with `NotRequired` optional fields (`3fa89af`, `d620769`, `6391048`) — a self-documenting record without class ceremony, letting mypy check field access while keeping dict ergonomics for sqlite/plist data. `isinstance` narrowing over `cast` (`3fa89af`: "Remove cast() by restoring isinstance check for proper type validation" — a cast asserts, a check verifies). `pathlib` over `os.path` (`3fa89af`); stdlib over subprocess when it suffices — `plistlib.load` handles binary plists, so the whole `plutil` dependency was deleted with evidence of testing against both formats (`1d14ce2`). Constants hoisted and named (`af3b75a`: `APPLE_EPOCH`, `APPLE_CONTAINERS`). Full annotations on every signature, including `-> None` on Click commands.

**2.7 Comment/docstring hygiene.** Public functions get a one-line docstring; private functions get none (`3d8bc5b` explicitly removes one "not required by ruff"); comments restating code are hunted in dedicated commits (`3cc2e39`, `ec91c40`, `6f786cc`). Motivation: a comment that repeats the code is a second copy that can lie. Unrepaired counterexample, worth flagging to the author: `cli.py` line 48 still carries `# This is a test comment to trigger pre-commit hooks.` (litter from the `da5e60e` pre-commit demo) — evidence that the hygiene requires active review, not that the rule changed.

## 3. Observed TDD cadence

**The commit unit is GREEN, then a burst of REFACTORs.** Per `<git_workflow>`, RED test + minimal implementation land as one `feat:`/`test:` commit; improvements land separately. The log shows the rhythm plainly: `eca50d2` feat → `bd9ea30`, `8bb84fb` refactor; `cffd595` feat → `e2653e3`, `ec91c40`, `087fb4b` refactor; `16fd70c` feat → `24dc928` refactor; `52a04c8` feat → `74e6220` refactor. In the gold period refactor-labeled commits outnumber feat commits roughly 3:1 — refactoring is the bulk of the work and each step is its own revertible unit. Motivation: every commit preserves a working state, so `git bisect` and `git revert` remain cheap tools, and the message history narrates *why* at each step.

**RED may be committed alone only when the red is the message.** Outside-in ATDD: a red acceptance test on main means "feature in progress" by design ("Red acceptance test = impl. in progress", `cdd7619`), so `1d1fb34` commits a deliberately failing test with a body explaining exactly why it fails. Everything else that must not run yet is committed as `skip` with its spec-docstring (§1.3) so the suite stays green.

**Corrections are full reverts with narrated lessons, then a redo in small steps.** `1b07bd5`, `bcb5223`, `82d3990`, `7d3922a`, `250230d` are wholesale reverts of the agent's own work. `7d3922a` carries the most instructive body in the repo: "We made a mistake — instead of refactoring the existing CLI tests… we created duplicate tests in a new file. This wasn't the goal." The redo (`45256cd` → `552a9a3` → `c52fc26` → `a596b6c` → `ceb4a1d` → `94e2af6` → `ef05821`) converts **one test at a time**, each commit body explaining what improved — `45256cd` even labels itself an intermediate step and announces "the next commit will show a better approach." Motivation: the revert-then-redo sequence turns a mistake into a documented pair of counterexample and exemplar; patching the mistake in place would erase the lesson.

**Refactoring never drops coverage silently.** Before converting CLI specs off subprocess, `5730bf4` first adds library-level filter tests explicitly "to ensure we maintain coverage when converting CLI tests from subprocess to mocks" — the safety net moves *before* the trapeze. Where a deliberate drop occurs it is declared and justified: `764c512` "Coverage drops to 94% but edge cases still tested at library level." Coverage is checked as a byproduct, never chased ("Coverage-Driven Development" was named as an anti-pattern in-session and the codebase reflects it: 100% was reached twice by *deleting* code, `e7a5fa4`, `aafeb0d`).

**Bug fixes arrive with the spec that names the corrected understanding.** `e72007f` fixes cloud detection and lands `_row_to_book` unit tests enumerating the ZSTATE×ZISSAMPLE truth table in the same commit — the test is the durable statement of what was learned (ZSTATE=6 is a *cloud sample*, hence both flags).

## 4. The gold standard, and exactly how the post-`6f786cc` lapse deviated

**What "gold standard" means here** (the state TODO.md wants restored): story card → failing acceptance spec whose docstring quotes the card → unit-level TDD inward → acceptance goes GREEN → refactor commits with honest labels; specs refactored in place, one at a time; mocks only at owned boundaries, real fixtures for integration; assertions at maximum layer-appropriate strength; defensive code only with demonstrated evidence; every commit body explaining why. `1d1fb34` (the last commit before the boundary, with `6f786cc` as the final style touch) is itself gold-standard RED: a failing acceptance test, committed alone, whose body names the missing collaborator.

**The lapse** (`af3954c`…`5b42ae0`, 2025-07-13/14, "YOLO mode", per `docs/yolo_mode_retrospective.md` + TODO.md). The deviations, each with its exact mechanism:

1. **Acceptance-first abandoned.** `5b42ae0` adds sample filtering to `list_recent_books` with unit test and implementation in one commit; no acceptance test existed or was created. `677a251` later adds them post-hoc, its body admitting they "should have been created before implementation." The cost is not ceremony: without the outside-in RED, there is no executable statement of *user-visible* done, so "done" regressed to "code exists."
2. **The spec was mutated to fit the code.** `1d1fb34`'s test patched `bookminder.apple_books.library.SUPPORTED_FILTERS` — that patch target *was* the spec: the CLI consults the library at call time. `fa0bc72` implemented with `from library import SUPPORTED_FILTERS` (an import-time copy the library patch can't reach) and then **edited the failing test's patch target to `bookminder.cli.SUPPORTED_FILTERS`** to go green. GREEN was achieved by weakening the claim, not satisfying it: the delegation property `1d1fb34` existed to prove was silently inverted, and the architectural decision was made inside a test edit nobody discussed.
3. **Commit labels stopped telling the truth.** `3d2bab6` strengthens the unit test (`len > 0` → exact set) *and* changes the implementation in one commit labeled `refactor:`; `ef5474b` adds new behavior (validation on `recent`) plus its test, also as `refactor:`. Refactor means behavior-preserving; mislabeling destroys the audit property the GREEN/REFACTOR commit split exists to provide — you can no longer trust the log to tell you which commits could have changed behavior.
4. **Defensive code without evidence returned.** `b246d7b` adds `(ZISSAMPLE != 1 OR ZISSAMPLE IS NULL)` — no NULL in any fixture, no evidence of NULLs in real data. This is the `e7a5fa4` failure recommitted verbatim in SQL, and it was corrected the same way: `c851f95` deletes it after checking the fixtures.
5. **Fake-strength assertions.** `b246d7b`'s CLI test asserts `"Sample Book" not in result.output` with only a regular book stubbed — unfalsifiable by construction (§1.10).
6. **Test structure hijacked.** `describe_bookminder_list_recent_command` was commandeered for filter validation and the original content displaced to `describe_bookminder_list_recent_command_with_fixtures` (visible as the before-state in `9cac7d7`'s diff): the describe names stopped being true sentences about their contents, which corrupts the `--spec` output — i.e. the requirements document itself.
7. **Symmetric features, divergent styles.** `!cloud` specified as a simple passthrough call-assertion, `!sample` as a mock-return-plus-output check — two idioms for one property, so a reader can no longer tell whether the difference is meaningful (retrospective: "Consistency Trumps Cleverness").

**Why it happened, per the project's own diagnosis:** optimizing for finishing over demonstrating; architectural decisions taken silently inside test edits; and "didn't fully appreciate BookMinder as a benchmark for process, not just a utility." The deepest reading: every YOLO commit *individually* looks TDD-shaped ("test: add failing unit test…", "minimal implementation…"), which is precisely the retrospective's warning — the vocabulary of the discipline survived while its causal order (story → acceptance RED → inward) did not. The style cannot be verified commit-by-commit; it is a property of the *sequence*.

**The repair arc and its limit.** `677a251` (retrospective + the missing acceptance tests) → `9cac7d7` (parameterized consistency) → `c851f95` (evidence-based simplification) → `be394a0`…`0bf00d1` (the four-layer split, making the mock/no-mock question answerable by directory and each layer's contract explicit in its `__init__` docstring). But the full semantic restoration to pre-YOLO (`447dc8c`, PR #18) was never merged: TODO.md still lists `validate-filter-values`, `filter-by-sample-flag`, `filter-by-reading-status` as needing "proper ATDD reimplementation" to "re-establish gold standard." The features work; the stories are nonetheless not accepted — because in this project a working feature without process provenance is, by definition, not done.

## Unrecovered motivations (stated honestly)

- Why the CLI error boundary asserts `exit_code == 0` even on `BookminderError` (`cb47cac`, current `cli_spec.py`) while validation errors exit 1: no commit explains the asymmetry; it may simply be unexamined.
- Why `describe_bookminder_acceptance`'s post-YOLO restoration tests (`677a251`) kept mock-return + output-string style rather than pure call-assertion style — plausibly deliberate (they specify formatting of filtered output end-to-end at the acceptance layer), but no commit body says so.
- The `# This is a test comment to trigger pre-commit hooks.` litter in `cli.py` (from `da5e60e`) survives every comment-hygiene sweep; no evidence this is intentional.
