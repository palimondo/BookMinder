# Goals and history — what BookMinder is for

## Destination and core question

- **B-01 — Destination.** An MCP tool for discussing books with Claude: the author reads on his iPhone and wants to talk with an LLM about the book he is reading, its last chapter, and the highlights made since the last conversation. CLI first, deliberately — the author knows CLI design and TDD/BDD cold, while MCP was unfamiliar territory; the CLI is the walking skeleton of the broader vision.
- **B-02 — Core question.** Can an LLM be a good pair programmer? The author had no colleagues to pair with; this project is the experiment. The method is the point: executable specifications nail verifiable invariants, and the art is slicing the problem and designing specs with minimal coupling to implementation — London school, GOOS lineage. The root principle everything else derives from: the spec's job is nailing requirements in a falsifiable way. Executable specification, GOOS layers, enforced layer separation, and delegation contracts all follow from falsifiability — a hierarchy, not parallel motivations.
- **B-03 — Why Apple Books as testbed.** Deliberately chosen because the Apple Books database schema is undocumented and evolves with each macOS release. That makes the project a test of long-term software evolution and maintenance — the opposite of one-shotting problems the model already knows from pretraining.
- **B-04 — Book-grounding motivation (product feeds process).** Pretrained simulacra of TDD/BDD experts proved shallow caricatures — skewed, non-actionable summaries of real positions. A core BookMinder motivation is giving the model access to full books as consultation material, so actionable principles can be extracted from primary sources that did not survive pretraining summarization. The failure-mode name for the thing this defeats: simulacra-shallowness.
- **B-05 — The project is a vehicle and a benchmark.** The real object of study is whether an AI coding agent can hold a strict ATDD process as a pair programmer. The process artifacts that count as deliverables are bounded: the durable chain (story cards expanded into acceptance tests, with working code as the output an agentic system must derive from them), the session diary, and the agent-instruction files (themselves WIP, their techniques untested — his words). AI-written retrospective meta-analysis is not one of them — the author calls it slop (see B-31), and every time he affirmed the vehicle framing he qualified it in the same breath, warning the meta-project could turn out to be a big baggage of AI slop in the end. The author (a Product Owner by day job, working in Jeff Patton's User Story Mapping tradition) has long intended the project to double as a benchmark of agentic coding systems.

## History

- **B-06 — BookMind, the predecessor.** BookMind implemented most of the original vision — EPUB parsing, highlight extraction, markdown export, a working CLI, 40 passing tests. It was not a failure. The fork to BookMinder was motivated by process, cost, and code quality: the agent took too much unrequested initiative and produced a sprawling codebase at high cost. Never describe BookMind as broken software, and never score BookMinder against BookMind on size, coverage, or feature count — BookMinder is a walking skeleton by explicit request, so the comparison measures the choice, not the outcome. `ORIGINAL_VISION.md` is a copy of BookMind's first README (verify with `git show 64dc71b:README.md` in the BookMind repo context), not a BookMinder-specific document.
- **B-07 — Scope discipline is the founding constraint.** BookMinder exists specifically to stop the agent from running ahead with its own creative ideas. The scope is the GOOS walking skeleton plus whatever the story cards ask for; add no capability the author has not asked for. CLAUDE.md is the instrument of that constraint.
- **B-08 — Apple-only by design.** Apple Books is the product's entire subject. Never propose, justify, or advertise a change on cross-platform grounds; CI pins macOS.
- **B-67 — Public by design.** The whole repository is public and the methodology is deliberately developed in the open — session diaries, mining corpora, eval design, coordination logs included. Do not treat pushing project material to this repo as an exposure event, and do not relay automated publication warnings about it; the exceptions that DO warrant stopping and asking are genuinely new content classes: credentials or tokens, third-party private data, or personal data beyond what the author has already published here.
- **B-09 — Timeline in brief.** Summer 2025: intense development — a gold-standard ATDD era, then a process lapse after commit 6f786cc (features landed without proper ATDD; the repair backlog for this still stands) — ending in the author's burnout from holding process discipline for models that knew the process but could not perform it (knowing vs performing is the key distinction). ~1 year dormant. 2026-08: reevaluation sessions on cloud infrastructure — no new feature code; the 2025 session diary was mined into a rules corpus, the spec tree was restored wholesale to its pre-reorg concern-based form, the commit-after-RED experiment was first restored and then retired by the author's ruling (git grammar proved an imperfect proxy for process compliance, which transcript analysis measures directly), the agent-instruction files were unified into one canonical rules file, and this skill was compiled.
- **B-10 — The stickiness law.** Corrections shipped as automation (hooks, validators, CI) stick; shipped as prose they only partly stick. The author rates Claude Code hooks the most valuable CC innovation for exactly this reason: enforcement via automation, not prose. When a rule keeps being violated, the durable fix is machinery, and the open experiment question is how much harness enforcement discipline requires once skills are in place.

# Repo geography, backlog, and fixture architecture

## Orientation

- **B-20 — Cheapest grounding.** `/hi` (and this skill) already supply the session-start census — read what you were given before running discovery commands of your own; re-deriving project structure by hand is what the author interrupts. The production package is tiny (`bookminder/cli.py` + `bookminder/apple_books/library.py`) — read it whole before any task; it is cheaper than guessing, and its current size is one `wc -l` away, never a remembered number. The behavior spec of the whole system is `pytest --spec`. Feature entry chain: `bookminder/cli.py` → `bookminder/apple_books/library.py`; everything else is docs, fixtures, or process. Never run unfiltered `find .` or repo-wide line counts — both this repo and BookMind keep a vendored venv in-tree, and the two raw line counts that once produced a "44% code reduction" headline were almost entirely site-packages; exclude caches, any vendored venv, and `claude-dev-log-diary/` from every listing or metric.
- **B-21 — Land mines.** `claude-dev-log-diary/` (a large body of hand-curated session transcripts) is permission-gated: never read, grep, commit, or surface it — including indirectly via `git diff`/`git show`/`git log -p` — without explicit user consent, and a grant is scoped to the exact excerpt and manner named (range reads of the named lines, not whole-file ingests — one whole-file read against an explicit line-range grant wasted 10% of context and drew a rebuke; and never from a background subagent, where the author cannot see or stop what is being read — he kills those on sight). One day-file may contain several sessions (`^claude` marks each start) and only the session-end cost figure is valid. `docs/ui/apple/` holds large binary screenshots — reference by path, never Read. `specs/apple_books/fixtures/All_Books*.swift` are large, grep-only, and deliberately untracked pending curation — do not gitignore them and never stage them. Fixture `.sqlite` files are binary — query with `sqlite3`, never Read. The `./xs` symlink resolves into the forbidden diary directory: execute it as the documented tool, do not read it as a file. Zero-byte fixture files (`401429854.epub`, corrupted_db_user's plist+sqlite) are intentional — that is the fixture's point, not damage to repair.
- **B-22 — Spec tree layout.** Specs are concern-based at HEAD: `specs/cli_spec.py`, `specs/cli_formatting_spec.py`, `specs/apple_books/library_spec.py`, `specs/apple_books/library_integration_spec.py`, with fixtures co-located under `specs/apple_books/fixtures/`. A 2025 four-layer reorg (`unit/integration/acceptance/e2e`) was reverted wholesale in 2026-08 by checkpoint restore; those directories may linger as untracked `__pycache__` residue only — they are not tracked structure (confirm with `git ls-files specs/`). Coverage caveat: `specs/cli_spec.py` drives the CLI via `subprocess` (`sys.executable -m bookminder`), and pytest-cov does not follow child processes — never read a coverage gap in subprocess-exercised code as evidence it is untested.

## Session-transcript preservation

- **B-32 — Native transcript backup (cloud/ephemeral containers only).** `claude-dev-log-diary/jsonl/` preserves full session transcripts in the agentic system's native format — the machine-readable source the day-files only shadow; layout and copy commands live in its README. When working in an ephemeral container (Claude Code cloud infra), the container's transcript dies with it, so snapshot the session's `.jsonl` file + directory from the harness project store (`/root/.claude/projects/<project>/`) into `jsonl/cloud-<year>/` and commit: (1) always toward session end, when the final branch push is being prepared; (2) incrementally at natural stable points — after a major phase of work lands, or when resuming after a long pause (the pause's tail is then on disk). Copies are append-only extensions, so re-snapshotting is always safe; batch the snapshot into an adjacent commit rather than making high-frequency snapshot-only commits. A transcript cannot contain its own final minutes — the true tail of a session is captured by the next session's first snapshot. Local (non-ephemeral) sessions are exempt: the harness store persists there, and the author owns backup timing.

## Backlog and stories

- **B-23 — Backlog practice.** Stories are YAML cards under `stories/` in story-map columns: `discover` covers listing, filtering, admin access, and error handling; `access` is controlling the Apple Books app; `review` is highlights and notes; `export` is text extraction. Every card carries a mandatory `status` from the vocabulary the instruction layer's backlog rules define — status only, no priority/assignee metadata (YAGNI). TODO.md's Discover Column is a bare list of story paths in implementation order: the order is the plan, so take the next story in order rather than offering a menu, and keep the list free of emoji, numbering, and per-item rationale. Completed Features is an immutable record of the journey — never reorder or remove entries; annotate a reopened story in place (`[REOPENED: ...]`); refactorings are not listed there (user-visible stories only); a doc deletion gets a one-line breadcrumb with its commit hash. Parked backlog items must carry enough of the HOW (mechanism, trigger, expected behavior) that a fresh session can execute them without asking.

## Settled design decisions in the code

- **B-24 — CLI shape.** `main` is a Click group; `list` is a subgroup declared `@main.group(name="list")` on a function named `list_cmd` — never name the function `list`, which shadows the builtin and breaks `list[Book]` annotations at import time (fix name collisions at the source, not with deprecated typing aliases). Subcommands `recent` and `all` share options via the `with_common_list_options` decorator (Click does not inherit group options). Filter vocabulary: one `--filter` option (single value at HEAD — multiple filters are deferred future work with no story yet) whose values are attribute names with `!` negation — `cloud`/`!cloud` and `sample`/`!sample` implemented today, with reading status (`finished`, `unread`, `in-progress`) already assigned to the same option by the approved plan; there is no `--flag`, no `--status`, and no `--type` — those were considered and reversed, so reintroducing one is reopening a settled decision, not a design choice. `!` and not `-` because Click parses a leading `-` as an option; filters are orthogonal to list commands (nothing in Apple Books' UI makes them command-specific). `list recent` deliberately replicates Apple's Continue section so that an agent consuming the future MCP surface and the human looking at the app share one frame of reference. `--user` is simultaneously a real admin feature (examine another user's books) and the test seam — the admin use case is what licenses it in production. The CLI owns no domain knowledge: it passes the raw `--user` string and filter through to the library and delegates path resolution and querying there.
- **B-25 — The Book type.** One `Book` TypedDict with `NotRequired` optional fields; never a parallel type for a variant that adds a field. Only `title` and `author` are required; `path` and `updated` are `NotRequired` — the type guarantees only what every code path can honestly supply, and the DB-backed path fabricates `path` as `""` (see the domain page's open path-correlation problem). TypedDict is a static annotation only: it produces a plain dict, no attribute access, no runtime key enforcement.

## Fixture architecture

- **B-26 — Synthetic $HOME personas and the front-door seam.** Integration fixtures are synthetic home-directory trees under `specs/apple_books/fixtures/users/<persona>/` replicating Apple's container layout path-for-path. Each persona encodes a container state observed on a real machine: `test_reader` (full library), `fresh_books_user` (all containers, empty plist, empty-schema sqlite), `legacy_books_user` (containers but no BKLibrary directory), `never_opened_user` (only the OS-created `com.apple.iBooksX` container, holding an empty `BKLibrary` directory and nothing else — no BKAgentService, no plist, no sqlite), `corrupted_db_user` (zero-byte plist and sqlite; note a corruption scenario needs the full container present or the plist check fires before the sqlite error). The legacy/never-opened split exists to exercise two distinct error paths in `library.py`: a missing `BKLibrary` directory raises "BKLibrary directory not found", an empty one raises "No BKLibrary database found in:" — which is why `never_opened_user`'s empty directory is load-bearing and kept tracked by its leaf `.gitkeep`. The seam is the front door: `--user` with an absolute path is used verbatim as the home directory, a bare name resolves to `/Users/<name>`, `None` to `Path.home()` — exactly three cases, specced in `library._get_user_path`, no falsy-string case. Specs must pass absolute fixture paths (a relative path is treated as a username and silently rewritten). This seam exists because fixtures through the product's own parameter exercise the real path-construction code, where patching a private module name would bypass it; the older module-constant seam (`BKLIBRARY_DB_FILE`-style) survives only with its known limitation — it is an in-process substitution resolved at import time and cannot cross a subprocess boundary.
- **B-27 — Fixture data discipline.** The fixture database carries the real schema verbatim — dump `.schema ZBKLIBRARYASSET` from a live database, never hand-write a schema. Rows are copies of real, complete book records: populate only with `specs/apple_books/fixtures/copy_book_to_fixture.sh` (ATTACH DATABASE + explicit column list minus Z_PK, generated from `PRAGMA table_info`), never hand-written or hand-edited SQL — an invented or edited row encodes the agent's beliefs exactly where the spec is supposed to be falsifiable. If a needed state does not exist, the author adjusts a real book in his library and it gets copied. Use the existing scripts (`create_fixture.sh` creates, `copy_book_to_fixture.sh` populates); if a script fails, debug the script. Scripts never delete — cleanup is a deliberate human act. Script rules: parameter variable is `FIXTURE_USER`, never `USERNAME` (a zsh special parameter that silently shadows the argument); SQL-escape titles by doubling quotes; locate the fixture DB by the same `BKLibrary-*.sqlite` glob production uses; root every path at PROJECT_ROOT and verify the resolved path before the first write (a swapped path once planted a stray fixture inside the real Apple Books directory). Document how each fixture was derived in `docs/test_fixtures.md` in the same commit. Preserve intentionally-empty directories with a single `.gitkeep` at the leaf. Prefer extending `test_reader` over new personas unless a test needs isolation. After any fixture change, verify through the product: `python -m bookminder list recent --user <absolute fixture path>`.
- **B-28 — Fixture census freshness.** Never rely on a remembered census of what `test_reader` contains — earlier remembered censuses went stale when books were swapped. The census truth is one query away: `sqlite3 "specs/apple_books/fixtures/users/test_reader/Library/Containers/com.apple.iBooksX/Data/Documents/BKLibrary/BKLibrary-fixture.sqlite" "SELECT ZTITLE, ZSTATE, ZISSAMPLE, ZREADINGPROGRESS FROM ZBKLIBRARYASSET"`. Lore: the zero-byte `401429854.epub` placeholder is "Growing Object-Oriented Software, Guided by Tests" — the project's canonical known book, named in ORIGINAL_VISION.md.
- **B-29 — Real DB vs fixtures.** Exploration of Apple Books behavior runs read-only against a real database — fixtures can only confirm what was built into them; when reality shows a new case worth capturing, it gets copied into the fixture. Fixtures freeze time — any recency-window behavior must be specified with controlled time, or the snapshot silently ages out of the window.
- **B-30 — Toolchain and environment.** Python pinned `==3.13.*` in `pyproject.toml` — pinning, not a permissive floor, because reproducibility across machines depends on one interpreter; uv + ruff + mypy, setuptools backend; ruff `target-version = "py312"` stays until the pinned ruff accepts py313. Run tests from the venv: `source .venv/bin/activate && pytest` (`uvx bookminder` fails — unpublished; bare `uv run` re-downloads CPython). A fresh checkout has no `.venv` — provision with `uv venv && uv pip install -e ".[dev]"`. When ruff disagrees between shell and hook, compare `.pre-commit-config.yaml`'s pinned `rev:` against `ruff --version` in the venv. `check-toml` stays in pre-commit — an invalid pyproject once passed an all-green run and broke the second machine.
- **B-31 — Repo maintenance principles.** Exactly one source of truth per concern; a migration deletes the superseded file inside itself. Never invent identity metadata — the author is Pavol Vaskovic (pali@pali.sk); ask or leave blank. An untested causal claim does not go into docs: if you assert X is required, remove X and show the failure first, and never document a command until you have run it and shown it working. Judge any document by whether it is referred back to and changes behavior on this project — retrospective meta-analysis docs fail both tests and the author calls them slop. README bash snippets carry no inline comments (readers copy-paste them); explanation goes in the prose above.

# Current state and open decisions

State claims rot. This page names where truth lives and which decisions are genuinely open; when it conflicts with the tree, the tree wins — then update this page.

## Where truth lives

- **B-60 — Read state, don't recall it.** System behavior: `pytest --spec`. Backlog and its order: `TODO.md`, with per-story status truth in the `stories/*/*.yaml` cards — where the two disagree the card wins and TODO.md is the stale one. Repair backlog: `.coordination/verified-residue.md`, a defect list in which every item carries its own check command; consult it there rather than duplicating it, and re-run an item's check before acting on it, because repair passes have landed since it was written and the file was not re-swept afterwards. Meta-session phase state — coordination in flight, review positions, what still awaits an author ruling: the HANDOFF at the top of `.coordination/threads.md`. Apple Books domain facts: the domain page, which states what is established and what is unknown; `docs/apple_books.md` for depth and evidence.

## Settled rulings — do not reopen them

- **B-61 — The plist API is a deliberate seed, not dead growth.** `library.list_books` and `find_book_by_title` are exercised only by specs and have no caller in `cli.py`; the author ruled that this is intentional — they are the seed of the future EPUB content path, since only `Books.plist` carries EPUB file paths — and README documents them as a pre-release library API whose sample matches the real signatures. Do not delete them, do not report the zero-caller grep as a finding, and do not re-derive the question: a smell that has been ruled on is a decision, not a defect.
- **B-62 — A feature without process provenance is not done.** The filter work that landed after the outside-in lapse is `reopened` on its story cards and annotated in place in TODO.md's Completed Features; the author's ruling is revert-and-redo through the full outside-in cycle — story card, failing acceptance spec, then inward — because "The discipline is the point. The outside-in ATDD.", not to keep code on the strength of it working. The plan, its sequencing, and what stays in the tree until the redo starts live in TODO.md's In Progress section; read them there rather than carrying a copy.

## Open author decisions — record, do not resolve

- **B-63 — The unspecified borrow.** `cli.py` imports `SUPPORTED_FILTERS` from the library — the CLI-borrows-library-vocabulary contract — but no spec asserts the identity: the library spec asserts set equality only, and the CLI spec patches the CLI's own attribute, which keeps passing if the CLI grows a private matching literal. The fix's shape is agreed — a one-line identity assertion, `assert cli.SUPPORTED_FILTERS is library.SUPPORTED_FILTERS` — but it is not ruled in and has not landed. Fold it into a repair story when one is started; never add it as a drive-by edit.
- **B-68 — The silent cloud filter on `list all`.** The shared vocabulary validates `--filter cloud`/`!cloud` for every list command, but `list_all_books` implements only the sample pair — a cloud value passes validation and silently returns the whole library. Distinct from the display-vs-filter divergence the domain page records under B-47: that is two predicates disagreeing, this is a predicate missing. An accepted-but-unimplemented filter value awaits the author's direction — a candidate for the filter redo, never a drive-by fix.

## Standing practice for repairs

- **B-64 — Doc and rule repair happens in author-approved passes, not on sight.** Rot found in README, `docs/`, or the instruction layer is recorded as a ledger entry carrying its check command and then left alone; the author green-lights a repair pass and that pass consumes the ledger — the README's built-vs-roadmap split, the deletion of a stale toolchain doc, and the instruction-layer corrections all landed that way. Every pass leaves residue behind: retired toolchain names still sit in `docs/`, and a pre-commit test comment still sits in production code. A rot finding is therefore something to verify, ledger, and surface — not a task to start.

## The meta layer and this skill's place in it

- **B-65 — `.coordination/` is working substrate, not repo rule.** It holds the meta-project: the mined rules corpus, the compile policy and eval design, the contradiction ledger carrying the author's rulings, the repair backlog, the process-detector suite, the memory-architecture record, and the tools that validate all of it. Nothing produced there is repo rule until the author ratifies it, and what he ratifies is landed into the repo's own files — so cite `.coordination/` as evidence and history, never as instruction. Whether any of it graduates into `docs/` or `stories/` is his call and has not been made. Blind spot to remember when citing mined records: the mining validator checks `quote:` fields only, so quoted text sitting in any other field was never verified verbatim.
- **B-66 — This skill is the project's memory.** The environment carries nothing across sessions; the git repo is the only substrate, and this skill is the explicit, loadable encoding of what the project is — the compiled successor of the 2025 session diary, which was the same cure for the same amnesia. When durable knowledge lands — a ruling, a schema verification, a settled decision — it belongs here or in the artifacts B-60 points at: knowledge that exists only in a conversation is already lost, and knowledge written to a machine-local memory store is worse than lost, because it silently forks the project's memory per machine. Write-routing by layer, one source of truth per concern: product-layer in-flight state (backlog order, story progress) goes to `TODO.md` and the `stories/` cards; meta-layer phase state (coordination decisions in flight, run state, review positions) goes to `.coordination/threads.md`; this skill takes only compiled facts the author has ratified. A meta-layer ruling must land its product consequences in the product files — a development session must never need the meta record to know what to build; that seam is what keeps the two layers honest, and `.coordination/memory-architecture.md` holds the reasoning so the split is not re-litigated. Keep this page's claims current: a fossilized memory is worse than none.

# BookMinder — Project Memory

BookMinder is a CLI (heading for MCP) that reads a user's Apple Books library — macOS-only by design — built as a live experiment in whether an LLM can be a good pair programmer under strict outside-in ATDD. It is a deliberately tiny product and a process laboratory: story cards, acceptance specs, and disciplined commits are deliverables alongside the code. The production package (`bookminder/cli.py` → `bookminder/apple_books/library.py`) is small enough to read whole before any task, and the suite under `specs/` is the system's documentation (`pytest --spec`).

This skill is the project's cross-session memory — the environment has none, the repo is the only substrate. Facts here carry their WHY, and what was never established is stated as unknown; where state can rot, the page points at the command or file that holds truth instead of restating it. It deliberately substitutes for any machine-local memory the environment offers: project knowledge written into a machine-local store cannot reach other machines or cloud sessions, so never store project learnings there. Memory is layered by concern, one source of truth each: this skill holds compiled facts the author has ratified; the product's episodic head is `TODO.md` — read it at load, the order is the plan, with status truth in `stories/` cards; a meta-session's episodic head (coordination, benchmark work) is owned by that session type's own skill and record, and is never mixed into product-development sessions.
