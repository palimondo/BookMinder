===== goals-and-history =====
# Goals and history — what BookMinder is for

## Destination and core question

- **B-01 — Destination.** An MCP tool for discussing books with Claude: the author reads on his iPhone and wants to talk with an LLM about the book he is reading, its last chapter, and the highlights made since the last conversation. CLI first, deliberately — the author knows CLI design and TDD/BDD cold, while MCP was unfamiliar territory; the CLI is the walking skeleton of the broader vision.
- **B-02 — Core question.** Can an LLM be a good pair programmer? The author had no colleagues to pair with; this project is the experiment. The method is the point: executable specifications nail verifiable invariants, and the art is slicing the problem and designing specs with minimal coupling to implementation — London school, GOOS lineage. The root principle everything else derives from: the spec's job is nailing requirements in a falsifiable way. Executable specification, GOOS layers, enforced layer separation, and delegation contracts all follow from falsifiability — a hierarchy, not parallel motivations.
- **B-03 — Why Apple Books as testbed.** Deliberately chosen because the Apple Books database schema is undocumented and evolves with each macOS release. That makes the project a test of long-term software evolution and maintenance — the opposite of one-shotting problems the model already knows from pretraining.
- **B-04 — Book-grounding motivation (product feeds process).** Pretrained simulacra of TDD/BDD experts proved shallow caricatures — skewed, non-actionable summaries of real positions. A core BookMinder motivation is giving the model access to full books as consultation material, so actionable principles can be extracted from primary sources that did not survive pretraining summarization. The failure-mode name for the thing this defeats: simulacra-shallowness.
- **B-05 — The project is a vehicle and a benchmark.** The real object of study is whether an AI coding agent can hold a strict ATDD process as a pair programmer. The process artifacts that count as deliverables are bounded: the durable chain (story cards expanded into acceptance tests, with working code as the output an agentic system must derive from them), the session diary, and the agent-instruction files (themselves WIP, their techniques untested — his words). AI-written retrospective meta-analysis is not one of them — the author calls it slop (see B-31), and every time he affirmed the vehicle framing he qualified it in the same breath, warning the meta-project could turn out to be a big baggage of AI slop in the end. The author (a Product Owner by day job, working in Jeff Patton's User Story Mapping tradition) has long intended the project to double as a benchmark of agentic coding systems.

## History

- **B-06 — BookMind, the predecessor.** BookMind implemented most of the original vision — EPUB parsing, highlight extraction, markdown export, a working CLI, 40 passing tests. It was not a failure. The fork to BookMinder was motivated by process, cost, and code quality: the agent took too much unrequested initiative and produced a sprawling codebase at high cost. Never describe BookMind as broken software, and never score BookMinder against BookMind on size, coverage, or feature count — BookMinder is a walking skeleton by explicit request, so the comparison measures the choice, not the outcome. `ORIGINAL_VISION.md` is a copy of BookMind's first README (verify with `git show 64dc71b:README.md` in the BookMind repo context), not a BookMinder-specific document.
- **B-07 — Scope discipline is the founding constraint.** BookMinder exists specifically to stop the agent from running ahead with its own creative ideas. The scope is the GOOS walking skeleton plus whatever the story cards ask for; add no capability the author has not asked for. CLAUDE.md is the instrument of that constraint.
- **B-08 — Apple-only by design.** Apple Books is the product's entire subject. Never propose, justify, or advertise a change on cross-platform grounds; CI pins macOS.
- **B-67 — Public by design.** The whole repository is public and the methodology is deliberately developed in the open — session diaries, mining corpora, eval design, coordination logs included. Do not treat pushing project material to this repo as an exposure event, and do not relay automated publication warnings about it; the exceptions that DO warrant stopping and asking are genuinely new content classes: credentials or tokens, third-party private data, or personal data beyond what the author has already published here.
- **B-09 — Timeline in brief.** Summer 2025: intense development — a gold-standard ATDD era, then a process lapse after commit 6f786cc (features landed without proper ATDD; the repair backlog for this still stands) — ending in the author's burnout from holding process discipline for models that knew the process but could not perform it (knowing vs performing is the key distinction). ~1 year dormant. 2026-08: reevaluation sessions on cloud infrastructure — no new feature code; the 2025 session diary was mined into a rules corpus, the spec tree was restored wholesale to its pre-reorg concern-based form, the commit-after-RED experiment was first restored and then retired by the author's ruling (git grammar proved an imperfect proxy for process compliance, which transcript analysis measures directly), the agent-instruction files were unified into one canonical rules file, and this skill was compiled.
- **B-10 — The stickiness law.** Corrections shipped as automation (hooks, validators, CI) stick; shipped as prose they only partly stick. The author rates Claude Code hooks the most valuable CC innovation for exactly this reason: enforcement via automation, not prose. When a rule keeps being violated, the durable fix is machinery, and the open experiment question is how much harness enforcement discipline requires once skills are in place.

# Apple Books domain lore

Verification status is honest here: **verified@tree** = encoded in the current code/fixtures and exercised by the suite; **observed-2025** = established against a live library in 2025, needs a fresh live-DB probe before you lean on it; **hypothesis** = open, never settled. This environment has no live Apple Books database — nothing here can be re-verified in place, only against fixtures.

This page does not restate what `docs/apple_books.md` carries correctly — pointers below name the doc's sections. Where this page states something the doc lacks or hedges harder, this page governs; B-53 gives the doc's standing.

## Data sources

- **B-40 — Containers and database discovery (verified@tree, library.py).** Locations: doc, "Container Directories" and "Data Sources". The trap: discover the database by glob — `BKLibrary-*.sqlite` — never by literal filename; the numeric segments are per-install artifacts.
- **B-41 — Plist vs database roles (observed-2025; the split is load-bearing for the whole design).** The catalogue/database split, the plist's incompleteness, and the `updateDate` publisher-revision hypothesis: doc, "Data Sources" and "Progress Data Sources Hierarchy". Only this page records: the `sort_by='updated'` feature was deleted as YAGNI precisely because that field's meaning was unknown; BookMinder cares about the user's relationship to the book, which lives in the database; and books lazy-download from iCloud, so a catalogue entry with no file on disk is a valid library entry — never filter books by on-disk file existence.
- **B-42 — Apple epoch (verified@tree, library.py).** Core Data timestamps count seconds from 2001-01-01 UTC, not 1970 — raw values look like plausible Unix times and are silently ~31 years wrong without the `APPLE_EPOCH` offset. Conversion detail: doc, "Apple Timestamp Format Details".

## The ZSTATE census — the project's signature reflex

- **B-43 — ZSTATE is a small enum whose census must be re-taken, not recalled.** Single-value stories about ZSTATE kept being revised by the next batch of real rows. The working set the code encodes (observed-2025, library.py) is the doc's 1 / 3 / 6 mapping ("Observed ZSTATE Mappings"), which also carries the full ZSTATE-5 evidence — **5 is an OPEN HYPOTHESIS, not a verified mapping**, until a live-DB re-census. Not absorbed by the doc: books showing the UI cloud icon were seen at ZSTATE 1, 3, and 6, while the doc maps 1 as a local book — that observation crossed devices (iPhone UI vs the Mac's database, where the same title can legitimately differ), so the two records stand unreconciled until a one-machine re-census. The standing method, the author's directive: enumerate all distinct values DB-first and characterize each — never reason UI-first from the values already seen.
- **B-44 — Sample detection is a composite predicate (verified@tree, library.py).** `is_sample` = `ZSTATE = 6 OR ZISSAMPLE = 1`; `ZISSAMPLE = 0` is never proof a book is not a sample. ZSTATE 6 is the common case, downloaded samples the edge case — cover both. The lifecycle hypothesis, the observed per-title flips, and the rule that per-title values are point-in-time and need a re-run query: doc, "Sample Book Handling". Only this page records the display/filter divergence at HEAD (verified@tree): `is_cloud` = `ZSTATE in (3, 6)` but `--filter cloud` matches `ZSTATE = 3` only — a cloud sample displays ☁️ yet is excluded by the cloud filter. The 3-only filter is where the author's revert of an unauthorized widening left it — reverted for landing before approval, not because the wider predicate was ruled wrong — so change neither side without his direction and a spec.
- **B-45 — ZCONTENTTYPE is unverified (hypothesis).** Likely 1 = book (EPUB), 3 = PDF; the doc hedges the mapping consistently ("Content Type Identification", Domain Language) — the hedged form governs.
- **B-46 — Column facts.** `ZTITLE` is not a key (observed-2025; duplicate-row detail in the doc's "BKLibrary SQLite Database" field list) — any title lookup must handle and explain duplicates or detection becomes non-deterministic. `ZISFINISHED = 1` is the sole definition of finished (observed-2025; doc, "Progress Edge Cases") — never require `ZREADINGPROGRESS = 1.0`. Only this page records: `ZLASTOPENDATE` was never NULL for rows with progress > 0 (observed-2025, 221 rows, 0 nulls) — the basis for not guarding it; re-verify before adding or removing guards (the doc's NULL-timestamp warnings are B-53 speculation, not observations).
- **B-47 — Samples and `list recent` (hypothesis).** The substance — samples never observed with progress, position tracked as a type-3 AEAnnotation row, the UI's "1%" complication — is the doc's "Sample Book Handling" working hypothesis. This page adds: both claims are second-hand (a relayed log-analysis summary plus the agent's own requirements reasoning, never a live probe), and since `list recent` filters on `ZREADINGPROGRESS > 0`, sample filtering there is structurally near-empty — library-wide sample listing belongs on `list all`.
- **B-48 — "Want to Read" is unresolved (hypothesis).** Computed-not-marked status and observed composition (unread-or-sample): doc, "Want to Read Section". Only this page records: the ordering was never established — the recorded ZCREATIONDATE conclusion rests on a known arithmetic error — and the rule: document observed database behavior, never inferred user intent; say "unknown" when the mechanism is unknown.

## Environment facts

- **B-49 — Container lifecycle (observed-2025 on real machines).** The user states are in the doc's "User State Scenarios" and are exactly what the fixture personas encode. Only this page records: reading another user's `~/Library` requires sudo — a plain `--user <name>` run fails with PermissionError.
- **B-50 — Plist mechanics.** `Books.plist` stores `Books` as an ARRAY of dicts — a dict-keyed-by-id variant parses without error and silently yields zero books (verified@tree: the code guards for list shape, library.py). Read with `plistlib.load(open(path, "rb"))` — it auto-detects binary and XML; never shell out to `plutil -convert`. For human/agent exploration, render plists as Swift literals: `plutil -convert swift -o out.swift Books.plist` — far more token-efficient than XML; that is what the `All_Books*.swift` dumps are.
- **B-51 — Path correlation is an open problem.** `_row_to_book` sets `path=""` pending a `ZASSETID`-keyed correlation with `Books.plist` (verified@tree, library.py; `path` is `NotRequired` on `Book` for the same reason). The doc lists a `ZPATH` column, but whether the database has any usable path column was never actually checked — the question was left as an acknowledged TODO at the author's direction — so "the path exists only in Books.plist" is a needs-live-DB guess, not an established schema fact. Acknowledged design debt, not an oversight.

## Working the database

- **B-52 — Query discipline.** Answer one-off questions with the `sqlite3` CLI directly — no throwaway .py scripts in the tree, no print-debugging through production code. Use targeted column lists, never `SELECT *` (blurb columns flood the context). Parameterize titles with `?` placeholders — hand-escaping apostrophes ("What's Our Problem?") fails repeatedly. When a diacritics-bearing title returns nothing, retry `LIKE` on the longest ASCII-only prefix before concluding the row is absent — the shell round-trip, not the database, is what fails. When probing N items with the same shape, batch with `IN (...)`.
- **B-53 — docs/apple_books.md epistemic status.** The doc is the captured output of the reverse-engineering phase, re-aligned with the project's recorded evidence where the record allowed; everything outside that re-checked core — its NULL-handling and Edge Cases speculation, its UI behavior insights — is still a guess written in the observational voice and still the thing under test, never the reference. Verify any attribute row-by-row against the UI screenshots in `docs/ui/apple/` and a live query, never against the doc's own prose. Editing rules the author enforces: the doc stays descriptive of storage (no SQL that prescribes a feature's filtering strategy); every SQL query lives in the single Database-to-UI-Mapping section other sections link to (two copies of one query is how it contradicted itself); UI quirks (cloud samples rendered "1%") are documented, never replicated in the implementation; screenshots are committed into docs/ and referenced inline next to the claims they support, each labelled with the platform that produced it (iPhone tiles and macOS list views use different attribute vocabularies — macOS "Complete" is a long-form percentage, not a status); preserve existing segmentation when updating contents.

## Session-transcript preservation

- **B-32 — Native transcript backup (cloud/ephemeral containers only).** `claude-dev-log-diary/jsonl/` preserves full session transcripts in the agentic system's native format — the machine-readable source the day-files only shadow; layout and copy commands live in its README. When working in an ephemeral container (Claude Code cloud infra), the container's transcript dies with it, so snapshot the session's `.jsonl` file + directory from the harness project store (`/root/.claude/projects/<project>/`) into `jsonl/cloud-<year>/` and commit: (1) always toward session end, when the final branch push is being prepared; (2) incrementally at natural stable points — after a major phase of work lands, or when resuming after a long pause (the pause's tail is then on disk). Copies are append-only extensions, so re-snapshotting is always safe; batch the snapshot into an adjacent commit rather than making high-frequency snapshot-only commits. A transcript cannot contain its own final minutes — the true tail of a session is captured by the next session's first snapshot. Local (non-ephemeral) sessions are exempt: the harness store persists there, and the author owns backup timing.

## Backlog and stories

- **B-23 — Backlog practice.** Stories are YAML cards under `stories/` in story-map columns: `discover` covers listing, filtering, admin access, and error handling; `access` is controlling the Apple Books app; `review` is highlights and notes; `export` is text extraction. Every card carries a mandatory `status` from the vocabulary the instruction layer's backlog rules define — status only, no priority/assignee metadata (YAGNI). TODO.md's Discover Column is a bare list of story paths in implementation order: the order is the plan, so take the next story in order rather than offering a menu, and keep the list free of emoji, numbering, and per-item rationale. Completed Features is an immutable record of the journey — never reorder or remove entries; annotate a reopened story in place (`[REOPENED: ...]`); refactorings are not listed there (user-visible stories only); a doc deletion gets a one-line breadcrumb with its commit hash. Parked backlog items must carry enough of the HOW (mechanism, trigger, expected behavior) that a fresh session can execute them without asking.

## Settled design decisions in the code

- **B-24 — CLI shape.** `main` is a Click group; `list` is a subgroup declared `@main.group(name="list")` on a function named `list_cmd` — never name the function `list`, which shadows the builtin and breaks `list[Book]` annotations at import time (fix name collisions at the source, not with deprecated typing aliases). Subcommands `recent` and `all` share options via the `with_common_list_options` decorator (Click does not inherit group options). Filter vocabulary: one `--filter` option (single value at HEAD — multiple filters are deferred future work with no story yet) whose values are attribute names with `!` negation — `cloud`/`!cloud` and `sample`/`!sample` implemented today, with reading status (`finished`, `unread`, `in-progress`) already assigned to the same option by the approved plan; there is no `--flag`, no `--status`, and no `--type` — those were considered and reversed, so reintroducing one is reopening a settled decision, not a design choice. `!` and not `-` because Click parses a leading `-` as an option; filters are orthogonal to list commands (nothing in Apple Books' UI makes them command-specific). `list recent` deliberately replicates Apple's Continue section so that an agent consuming the future MCP surface and the human looking at the app share one frame of reference. `--user` is simultaneously a real admin feature (examine another user's books) and the test seam — the admin use case is what licenses it in production. The CLI owns no domain knowledge: it passes the raw `--user` string and filter through to the library and delegates path resolution and querying there.
- **B-25 — The Book type.** One `Book` TypedDict with `NotRequired` optional fields; never a parallel type for a variant that adds a field. Only `title` and `author` are required; `path` and `updated` are `NotRequired` — the type guarantees only what every code path can honestly supply, and the DB-backed path fabricates `path` as `""` (see the domain page's open path-correlation problem). TypedDict is a static annotation only: it produces a plain dict, no attribute access, no runtime key enforcement.

## Fixture architecture

- **B-26 — Synthetic $HOME personas and the front-door seam.** Integration fixtures are synthetic home-directory trees under `specs/apple_books/fixtures/users/<persona>/` replicating Apple's container layout path-for-path. Each persona encodes a container state observed on a real machine: `test_reader` (full library), `fresh_books_user` (all containers, empty plist, empty-schema sqlite), `legacy_books_user` (containers but no BKLibrary directory), `never_opened_user` (only the OS-created `com.apple.iBooksX` container, holding an empty `BKLibrary` directory and nothing else — no BKAgentService, no plist, no sqlite), `corrupted_db_user` (zero-byte plist and sqlite; note a corruption scenario needs the full container present or the plist check fires before the sqlite error). The legacy/never-opened split exists to exercise two distinct error paths (verified@tree, library.py:26-37): a missing `BKLibrary` directory raises "BKLibrary directory not found", an empty one raises "No BKLibrary database found in:" — which is why `never_opened_user`'s empty directory is load-bearing and kept tracked by its leaf `.gitkeep`. The seam is the front door: `--user` with an absolute path is used verbatim as the home directory, a bare name resolves to `/Users/<name>`, `None` to `Path.home()` — exactly three cases, specced in `library._get_user_path`, no falsy-string case. Specs must pass absolute fixture paths (a relative path is treated as a username and silently rewritten). This seam exists because fixtures through the product's own parameter exercise the real path-construction code, where patching a private module name would bypass it; the older module-constant seam (`BKLIBRARY_DB_FILE`-style) survives only with its known limitation — it is an in-process substitution resolved at import time and cannot cross a subprocess boundary.
- **B-27 — Fixture data discipline.** The fixture database carries the real schema verbatim — dump `.schema ZBKLIBRARYASSET` from a live database, never hand-write a schema. Rows are copies of real, complete book records: populate only with `specs/apple_books/fixtures/copy_book_to_fixture.sh` (ATTACH DATABASE + explicit column list minus Z_PK, generated from `PRAGMA table_info`), never hand-written or hand-edited SQL — an invented or edited row encodes the agent's beliefs exactly where the spec is supposed to be falsifiable. If a needed state does not exist, the author adjusts a real book in his library and it gets copied. Use the existing scripts (`create_fixture.sh` creates, `copy_book_to_fixture.sh` populates); if a script fails, debug the script. Scripts never delete — cleanup is a deliberate human act. Script rules: parameter variable is `FIXTURE_USER`, never `USERNAME` (a zsh special parameter that silently shadows the argument — this bug is fixed at HEAD, copy_book_to_fixture.sh:8); SQL-escape titles by doubling quotes; locate the fixture DB by the same `BKLibrary-*.sqlite` glob production uses; root every path at PROJECT_ROOT and verify the resolved path before the first write (a swapped path once planted a stray fixture inside the real Apple Books directory). Document how each fixture was derived in `docs/test_fixtures.md` in the same commit. Preserve intentionally-empty directories with a single `.gitkeep` at the leaf. Prefer extending `test_reader` over new personas unless a test needs isolation. After any fixture change, verify through the product: `python -m bookminder list recent --user <absolute fixture path>`.
- **B-28 — Fixture census freshness.** Never rely on a remembered census of what `test_reader` contains — earlier remembered censuses went stale when books were swapped. The census truth is one query away: `sqlite3 "specs/apple_books/fixtures/users/test_reader/Library/Containers/com.apple.iBooksX/Data/Documents/BKLibrary/BKLibrary-fixture.sqlite" "SELECT ZTITLE, ZSTATE, ZISSAMPLE, ZREADINGPROGRESS FROM ZBKLIBRARYASSET"`. Lore: the zero-byte `401429854.epub` placeholder is "Growing Object-Oriented Software, Guided by Tests" — the project's canonical known book, named in ORIGINAL_VISION.md.
- **B-29 — Real DB vs fixtures.** Exploration of Apple Books behavior runs read-only against a real database — fixtures can only confirm what was built into them; when reality shows a new case worth capturing, it gets copied into the fixture. This cloud environment has no live Apple Books library, so any exploration here runs against fixtures only: say so explicitly and mark conclusions provisional. Fixtures freeze time — any recency-window behavior must be specified with controlled time, or the snapshot silently ages out of the window.
- **B-30 — Toolchain and environment.** Python pinned `==3.13.*` (pyproject.toml:11) — pinning, not a permissive floor, because reproducibility across machines depends on one interpreter; uv + ruff + mypy, setuptools backend; ruff `target-version = "py312"` (pyproject.toml:71) stays until the pinned ruff accepts py313. Run tests from the venv: `source .venv/bin/activate && pytest` (`uvx bookminder` fails — unpublished; bare `uv run` re-downloads CPython). The cloud environment may arrive with no `.venv` — provision with `uv venv && uv pip install -e ".[dev]"`. When ruff disagrees between shell and hook, compare `.pre-commit-config.yaml`'s pinned `rev:` against `ruff --version` in the venv. `check-toml` stays in pre-commit — an invalid pyproject once passed an all-green run and broke the second machine.
- **B-31 — Repo maintenance principles.** Exactly one source of truth per concern; a migration deletes the superseded file inside itself. Never invent identity metadata — the author is Pavol Vaskovic (pali@pali.sk); ask or leave blank. ## Standing practice for repairs

- **B-64 — Doc and rule repair happens in author-approved passes, not on sight.** Rot found in README, `docs/`, or the instruction layer is recorded as a ledger entry carrying its check command and then left alone; the author green-lights a repair pass and that pass consumes the ledger — the README's built-vs-roadmap split, the deletion of a stale toolchain doc, and the instruction-layer corrections all landed that way. Every pass leaves residue behind: retired toolchain names still sit in `docs/`, and a pre-commit test comment still sits in production code. A rot finding is therefore something to verify, ledger, and surface — not a task to start.

## The meta layer and this skill's place in it

- **B-65 — `.coordination/` is working substrate, not repo rule.** It holds the meta-project: the mined rules corpus, the compile policy and eval design, the contradiction ledger carrying the author's rulings, the stamped repair backlog, the process-detector suite, the memory-architecture record, and the tools that validate all of it. Nothing produced there is repo rule until the author ratifies it, and what he ratifies is landed into the repo's own files — so cite `.coordination/` as evidence and history, never as instruction. Whether any of it graduates into `docs/` or `stories/` is his call and has not been made. Blind spot to remember when citing mined records: the mining validator checks `quote:` fields only, so quoted text sitting in any other field was never verified verbatim.
- **B-66 — This skill is the project's memory.** The environment carries nothing across sessions; the git repo is the only substrate, and this skill is the explicit, loadable encoding of what the project is — the compiled successor of the 2025 session diary, which was the same cure for the same amnesia. When durable knowledge lands — a ruling, a schema verification, a settled decision — it belongs here or in the artifacts B-60 points at: knowledge that exists only in a conversation is already lost, and knowledge written to a machine-local memory store is worse than lost, because it silently forks the project's memory per machine. Write-routing by layer, one source of truth per concern: product-layer in-flight state (backlog order, story progress) goes to `TODO.md` and the `stories/` cards; meta-layer phase state (coordination decisions in flight, run state, review positions) goes to `.coordination/threads.md`; this skill takes only compiled facts the author has ratified. A meta-layer ruling must land its product consequences in the product files — a development session must never need the meta record to know what to build; that seam is what keeps the two layers honest, and `.coordination/memory-architecture.md` holds the reasoning so the split is not re-litigated. Keep this page's claims verified or stamped: a fossilized memory is worse than none.
