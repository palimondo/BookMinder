     6	# Outside-in BDD/TDD Discipline
     7	
     8	The root principle, and the hierarchy that follows from it: a spec's job is nailing REQUIREMENTS IN A FALSIFIABLE WAY. Everything else in this skill is a consequence, not a parallel motivation — executable specification (specs, not prose, are the requirements document, because prose cannot fail), layer separation (each requirement lives at the one layer that can falsify it), and delegation contracts (boundary specs pin the conversation between layers, because that conversation is itself a requirement). When two rules seem to conflict, resolve toward whichever keeps the requirement falsifiable.
     9	
    10	Code is a liability, not an asset: the work is minimizing what must be written while the spec suite maximizes what is pinned. The discipline's value lies in the sequence, not the artifacts — rushing to implementation destroys it even when the resulting code looks correct, and the bet is rigorous process over one-shotting.
    11	
    12	## Invariants — in force at every moment
    13	
    14	- Never write implementation without a failing spec that demanded it; run the spec and watch it fail before writing any code, and say so explicitly.
    15	- Never weaken, rewrite, or skip an existing spec to get green: the expectation is the requirement, so when spec and code disagree, decide which is wrong before editing either.
    16	- Three commits per cycle: RED (the failing spec, committed before implementation), GREEN (minimal implementation), REFACTOR (each improvement separately, if any). RED commits and deliberately-red acceptance specs are the sanctioned exceptions to all-commits-passing.
    17	- One spec red at a time; one scenario at a time; remaining scenarios wait as skipped placeholders.
    18	- Specs render as prose: describe_/it_ names plus `pytest --spec` are the living requirements document; no docstrings on implemented specs.
    19	- Minimal constraint that still falsifies: implement only what the red spec demands, assert only what the requirement names, delete what nothing specifies.
    20	- Nothing is done until it has been executed and observed; report the command and its output, never the claim alone.
    21	
    22	## Page map — read the page before acting on the triggering task
    23	
    24	- Starting a story; acceptance criteria in hand; a red acceptance spec on the main line; tempted to fake it green; standing up a walking skeleton → `references/outside-in.md`

     1	# Assertion integrity — pin the requirement, nothing else
     2	
     3	An assertion is a falsifiable claim about a requirement. Calibrate both ways: maximal constraint on what the requirement names, zero constraint on what it does not.
     4	
     5	- **T-50** Express the minimal constraint that still falsifies — fewest fields, fewest assertions, shortest expression; one positive example suffices, so do not enumerate negative cases alongside it — extra examples add maintenance surface without adding constraint.
     6	- **T-51** Before calling a spec meaningful, check whether it would still pass against a stub returning an empty collection, and guard every loop or conditional assertion with a non-emptiness assertion — type checks plus `if x:` are satisfied by a function that does nothing, so the spec certifies the stub instead of the requirement.
     7	- **T-52** Assert exact identity sets where membership IS the requirement (the census is known, so anything weaker throws information away); never encode a behavioral contract — a limit, a cap, a recency window — via fixture cardinality, because a count pins nothing the requirement names and breaks when the fixture grows. Test limit properties at the layer that controls volume.
     8	- **T-53** Never weaken an assertion to make it pass against the fixture you happen to have, and never repair an unconditionally-true assertion by hardcoding a fixture-derived number — when the only available assertion would couple to incidental fixture shape, mark FIXME naming the right technique and owning layer, and move on.
     9	- **T-54** When a fixture-backed assertion fails, decide whether the named datum is the requirement or incidental: if it is the requirement, fix the fixture to contain it — rewriting the expectation to match the data destroys the requirement the spec encoded; if it is incidental, correct the expected value to what the fixture actually contains. Either way keep the assertion at full strength — a relaxed assertion turns a discovered mismatch into a permanently unfalsifiable claim.
    10	- **T-55** When production output changes and a spec fails, decide and state which of the two is wrong before editing either — an assertion rewritten to match observed output stops being a specification and becomes a transcript of current behavior. Never change an asserted literal under an unchanged it_ name: if the specified behavior changed, the name changes with it, because otherwise a different contract hides under the same sentence in the living documentation.
    11	- **T-56** Before rewriting an existing spec, enumerate the properties it constrains and show the replacement constrains each one; if it does not, say so instead of proposing the edit — replacements silently drop contracts under unchanged names.
    12	- **T-57** Never write a disjunctive assertion — a test that passes under two contradictory outcomes asserts nothing and can never go red for the right reason.
    13	- **T-58** Assert the presence of correct behavior, never the absence of a specific wrong implementation — negative space is unbounded, the assertion cannot fail for the right reason, and it becomes a historical artifact the moment the wrong implementation is gone.
    14	- **T-59** Prefer the assertion that names the property over one that hardcodes incidental content, paired with a non-emptiness guard — pinning a particular datum couples the spec to fixture churn rather than to the behavior. Never write an assertion whose expected value is an accident of the current fixture (e.g. encoding a fixture's emptiness) — it passes without the feature existing; if the fixture cannot exhibit the behavior, fix the fixture first. Before asserting on specific data, run the product against the fixture and read the actual output — an assertion invented from memory can name data that was never there.
    15	- **T-60** On an error-path spec, assert both the user-facing message and a fragment unique to the path under test (a discriminating message or path fragment) — a message shared by several failure paths stays green for the wrong reason indefinitely, and the discriminating fragment is what converts "an error happened" into a falsifiable claim about which error happened. Keep both assertions: they specify different requirements — what the user is told, and which internal path produced it.
    16	- **T-61** Do not pin what the requirement does not own: no absolute machine paths or full internal message text in acceptance assertions — every unrelated wording or path change then breaks the spec for reasons unrelated to the behavior it names.
    17	- **T-62** Delete a spec that a stronger spec already subsumes, then sweep the file for other instances of the same redundancy — whole-output equality already pins ordering, content, and absence, so the weaker check adds maintenance without falsifying power, and redundancy comes in clusters.
    18	- **T-63** Configure nothing on a mock that the test does not later assert on — an unused return value implies the test cares about something it never checks. In a coordination spec, assert the exact call sequence (call_args_list): it subsumes the count, and output assertions belong to the collaborator's own spec.
    19	- **T-64** If a mock makes an argument irrelevant, the spec does not constrain that argument — fix the seam; do not relabel the argument as a dummy to make the vacuity tidy, because documenting that a test proves nothing is not the same as making it prove something.
    20	- **T-65** A green counts as evidence only if you can name what would have made it red: after installing a test seam, prove the seam took effect (item counts, run time, the path actually read) before treating the pass as a result — an inert seam leaves the suite green against the wrong data, proving nothing.

     1	# The cycle and its commits — RED, GREEN, REFACTOR
     2	
     3	## RED — earn the failure
     4	
     5	- **T-10** Run the specific new spec and observe it fail before writing any implementation, and say so explicitly; re-run it after every edit to the spec itself — a spec that has never been executed in a failing state has not been shown to be capable of failing at all.
     6	- **T-11** Any failure that tells you what to build next is legitimate RED — import errors, missing modules, and unfinished environment setup included; record the failure and let it drive the next minimal step rather than clearing it before declaring RED, because demanding an assertion failure specifically would skip the steps that build the package itself.
     7	- **T-12** When a newly written spec passes on its first run, stop and treat that as a defect in the spec, not a completed step — a test that was never red proves nothing about the behavior it names.
     8	- **T-13** To prove a new assertion on already-green code can fail, implement the opposite behavior on purpose, watch the red, then revert — adding an assertion that has never failed proves nothing about the assertion.
     9	- **T-14** Commit after RED: commit the failing spec before writing any implementation — because the commit-per-phase record makes every cycle state rewindable, the log becomes the proof that a falsifier preceded the implementation, and the bet is rigorous process over one-shotting. RED commits and deliberately-red acceptance specs are the sanctioned exceptions to all-commits-passing.
    10	
    11	## GREEN — the minimum that passes
    12	
    13	- **T-15** Write the minimum production code that passes the failing spec: only the branch the red spec demands, never the symmetric or negated case — the opposite case is a separate scenario with no failing spec pulling it into existence, so it would ship untested.
    14	- **T-16** When adding an element to working output, append to the existing expression rather than restructuring it in the same change — a rewrite silently alters output other specs already own, converting a feature addition into an unreviewed regression.
    15	- **T-17** Run the full suite, then commit the passing spec plus minimal implementation immediately after GREEN, before starting any refactoring — refactoring on top of an uncommitted GREEN destroys the revertible checkpoint the cycle exists to create.
    16	
    17	## REFACTOR — a phase, not an afterthought
    18	
    19	- **T-18** After every GREEN, explicitly ask whether to refactor and either name the duplication found or state that there is none, before starting the next behavior; if the refactor phase gets abandoned for a digression, return to it before the next story — a cycle left at GREEN is unfinished, and the next story buries the evidence.
    20	- **T-19** Refactor the specs too, in their own commit — tests are code and decay exactly like implementation.
    21	- **T-20** One refactoring per commit; when two improvements entangle, land the one that is ready and return to the other — a commit that mixes two refactorings can be neither reviewed nor reverted as either. Commit after REFACTOR as the cycle's third commit whenever any refactoring was done.
    22	- **T-21** A `refactor:` label is a machine-checkable claim that behavior was preserved; never use it on a commit that changes behavior, removes an error path, or rewrites the expectations that would have caught the change — mislabelling destroys the log's audit property.
    23	- **T-22** A rename lands as its own increment and replaces: delete every occurrence of the old name in one sweep across production and specs, run the full suite before committing, and never un-skip a pending scenario or start the next feature inside the same change — a half-finished rename fails only at the untouched call site, and a mixed increment is unsafe to verify or revert.
    24	- **T-23** Before changing or relaxing a declaration you did not write, run git blame on it and grep every call site, then state the motivation you recovered — the constraint may be load-bearing for a path you have not read, and the history is cheap to consult while the removal is not.
    25	- **T-24** Fix a whole class of failures at its single origin, never case-by-case at each site — per-site patching leaves the same defect available to the next spec that is written.
    26	- **T-25** State which phase of the cycle you are in before proposing the next action — improvements offered in the wrong phase are undisciplined work however good they look.
    27	
    28	## Feedback loop and gates
    29	
    30	- **T-26** Run the suite and coverage after every single edit, combined into one command, not after a batch — batching hides which change broke or un-covered what and destroys the incremental commit boundary.
    31	- **T-27** Before committing, run the whole gate explicitly — formatter, linter, type check, full suite, coverage — and show each output rather than claiming you ran it; run the full suite locally before every push, never using CI as the first place a change is exercised.
    32	- **T-28** Never bypass a failing quality gate (skip flags, no-verify, silencing markers): the block is information about your workflow, so fix the cause and let the gate itself prove the fix. Treat tool warnings and "Skipped / no files to check" as part of the failing state — a gate that inspected nothing is a gap, never a pass.
    33	- **T-29** Nothing is done until it has been executed and observed: before claiming a change is ready, run it — the documented command, the suite, the config, the migration — and report the command and its output. Reproduce a reported failure by running the project's own documented command before proposing a fix, verify locally before publishing, and confirm on the remote that a pushed change actually landed.
    34	- **T-30** Treat a failing or empty test run as a fact about your own invocation until proven otherwise — activate the environment, retry, and read the retry's output before any conclusion that depends on it — because an unexamined tool error silently becomes a false premise for every downstream claim.
    35	- **T-31** When a fix attempt does not change the observed symptom, revert it before trying the next hypothesis, and say out loud that it did not help — keeping inert fixes stacks unverified variables and later gets them documented as essential.
    36	- **T-32** Undo a landed change with git revert, never by hand-reconstructing the earlier state — a hand-written inverse is unverifiable and loses the record that the change was deliberately undone; after a revert, grep the tree for the reverted mechanism rather than trusting the revert's range to have removed all of it.
    37	- **T-33** Commit story-card and requirements changes on their own before touching any spec or implementation — separating what-we-want from how-we-did-it keeps the requirement revertible and citable from the implementation commit.
    38	- **T-34** To establish what a codebase actually implements, run its suite and read the `--spec` output — never infer implemented scope from directory listings, module names, or summaries, because the executing suite is the only description of the system that cannot silently rot away from it.
    39	- **T-98** A commit message may claim only what the staged diff does: read the diff of every file you are about to describe — including files changed by hand — before writing the message, because the log is an audit record and a message describing a different change destroys its value as one.

     1	# Layers, seams, fixtures, and doubles
     2	
     3	Layer separation follows from falsifiability: each requirement is tested at the one layer that can falsify it, and the conversation between layers is itself a requirement, pinned by a delegation contract.
     4	
     5	## Layer ownership
     6	
     7	- **T-66** Test each behavior at exactly one layer — the layer that can falsify it: unit specs own domain mapping (raw value to domain field), integration specs own data selection (which records the query returns), acceptance specs own coordination and user-visible output — an acceptance spec that knows a domain detail has absorbed a rule that belongs below, duplicates that layer, and breaks when implementation details move.
     8	- **T-67** Classify each spec by what it depends on (the GOOS vocabulary): a spec that reads a real machine's state is an integration test, and only machine-independent specs gate CI — mislabelling an integration test as a unit test is what makes CI unreliable.
     9	- **T-68** When a spec fails on one machine and passes on another, first ask whether the divergent state is a legitimate product state the implementation wrongly excludes, and only then treat it as a test defect — diagnosing a real bug as "brittle test, mock it" ships the bug.
    10	- **T-69** One spec per behavior across the whole suite: never a second copy of a spec for a second environment or layer — decide which layer owns the behavior, because two suites specifying one behavior will eventually disagree and then neither is authoritative.
    11	- **T-70** A boundary spec mocks the collaborating subsystem and asserts the delegation contract only — the error surfaced to the user, no traceback leaked, the collaborator called correctly — never the lower layer's specific cases, which its own specs already own; one representative case proves the contract, and this is also why a boundary spec must not depend on any fixture being configured just so.
    12	- **T-71** Keep exactly one subprocess end-to-end spec whose only job is proving the wiring — it is the only spec that exercises the real entry point — and run every other spec in-process at its own layer, because a second subprocess spec only re-tests behavior, slowly.
    13	
    14	## Seams
    15	
    16	- **T-72** Fixtures enter through the front door — the product's own parameter (a synthetic home directory, an explicit path argument) — never by monkeypatching a private name, which couples the spec to an implementation identifier and bypasses the very path-construction code the spec claims to test. A module-constant seam is substitutable in-process only (it is resolved at import time and unpatchable across a process boundary); state that limitation whenever you rely on one.
    17	- **T-73** Choose the seam before writing the assertion: monkeypatch mutates the current interpreter only and cannot influence anything launched as a subprocess — a patch that cannot reach the code under test produces a red that proves nothing and masquerades as legitimate RED.
    18	- **T-74** Keep test-environment knowledge out of production code: a production function must never branch on identifiers that exist only in the spec tree — the shipped program would behave differently for names the user cannot see.
    19	- **T-75** Never encode the developer's home directory, username, or machine into production code, tooling, or assertions — a spec or script that only passes on one machine specifies that machine, not the behavior.
    20	
    21	## Fixtures
    22	
    23	- **T-76** Fixtures are observations, not constructions: build them by copying complete records out of the real system and reducing to the minimal set the scenarios need — never hand-author rows, invent field values, or create a fixture whose only justification is reaching an uncovered branch, because an invented fixture encodes your beliefs and the spec then verifies your own stub. Explore the real system read-only; extend the fixture only when reality shows a case worth capturing.
    24	- **T-77** Never edit a fixture to make a failing spec pass while the domain fact it encodes is still unknown — a fixture bent to fit a guess makes the guess unfalsifiable and the spec meaningless; validate the assumption against the real source first.
    25	- **T-78** Any behavior gated on a time window is specified with controlled time — fixtures are frozen snapshots, so a recency assertion against them silently rots into a false pass or a false fail.
    26	- **T-79** When a spec depends on an otherwise-empty directory tree, commit a single `.gitkeep` at the leaf — git tracks files, not directories, so an untracked fixture tree is silently destroyed and the spec then passes for the wrong reason.
    27	
    28	## Doubles
    29	
    30	- **T-80** The double's name states what the test is for: a double that only supplies data is a stub (a plain dict will do); reach for a Mock only when the spec verifies calls — a Mock where a stub suffices implies an interaction assertion that never happens.
    31	- **T-81** For pure-function specs, build inputs with a stub helper that defaults every field (`row_stub(**overrides)`) and name in each call only the fields under test; construct test objects with only the fields the assertion depends on — irrelevant fields hide the variable being varied and falsely signal that their values matter.
    32	- **T-82** Name a patch handle after the full function being patched (`mock_list_recent`, not `mock_list`) — a truncated handle becomes ambiguous the moment a sibling collaborator is patched in the same file.
    33	
    34	## Restructuring a suite
    35	
    36	- **T-83** Move coverage before you remove it: land the replacement specs at the new layer and see them pass before deleting the specs they replace, and before converting or deleting an end-to-end spec, locate which lower-layer spec covers each behavior it carried and add the missing ones first — the gap between delete and replace is a window in which the behavior is unspecified, and that window is where regressions enter.
    37	- **T-84** Probe test-architecture coupling by deliberate mutation: break one implementation detail (drop a column, misspell a key), run the whole suite, record which specs fail, revert — the blast radius of a one-line change is the objective measure of how much each layer knows about the layer below. Then restructure toward a target stated as a falsifiable sentence ("after this, only the N specs that own that detail fail on that mutation") and re-check it after each step — a restructuring with a goal but no test for the goal cannot be judged to have succeeded.

     1	# Minimal implementation, YAGNI, and coverage
     2	
     3	Code is a liability: every line must have been demanded by a failing spec, and an uncovered line is evidence of code nothing demanded — the fix is removal, not a retroactive test.
     4	
     5	- **T-85** No implementation without a failing spec that demanded it; if implementation was edited ahead of a spec, revert it to the pre-edit state before proposing anything — without a spec pulling against it, the change is editorial fiat, and there was no moment at which a failing test drove the behavior into existence.
     6	- **T-86** Write no defensive code that no spec demanded — no existence guards, no blanket exception handlers that print and return an empty default, no fallbacks added for "consistency" or "to be safe" — untested defensive code is unspecified behavior that can be wrong invisibly, and a silent guard can BE the bug. When you find one already written, delete it rather than adding a test to cover it — a test written after reading the implementation can only ratify it.
     7	- **T-87** Before adding any guard or conversion, demonstrate the case occurs: query the real data source and report the counts, or execute the path and observe the actual exception type; if the case cannot occur, delete the guard and narrow the type signature instead — and check the query that produced the data, because a case the query already excludes is dead code in the guard that merely suggests to the reader that it could occur.
     8	- **T-88** An uncovered line is evidence that code exists which no requirement asked for: trace its provenance (git log -S, git blame) and ask whether any spec ever demanded it, then delete the code — never write a test whose stated purpose is to execute a line the coverage report flagged, because that inverts the discipline the metric is supposed to measure.
     9	- **T-89** Coverage is a diagnostic residue of good specs, never a target: never retrofit tests to raise the number, and never dismiss a gap as "defensive programming not worth testing" without first checking reachability and provenance — both moves were wrong every time they were tried.
    10	- **T-90** Never justify deleting a spec by "coverage stayed flat": coverage measures line execution, not contract specification, so a boundary-contract spec can be unique while contributing zero coverage; prove redundancy by showing a code mutation the remaining specs still catch — and after restoring a doubted spec, introduce the bug it claims to catch, watch it fail, revert, and record the demonstration in the commit message.
    11	- **T-91** When a production change breaks an existing spec, repair the spec or revert the change; never add a skip marker to restore green — skipping converts a failing requirement into an invisible one.
    12	- **T-92** Delete any capability the current fixtures cannot falsify — untestable-now is the YAGNI detector: a parameter, branch, and test that no fixture can exercise are all decoration.
    13	- **T-93** Create only the directories and files a current spec demands and delete speculative scaffolding as soon as it is noticed; apply YAGNI to docs and tooling exactly as to code — no documentation for unadopted tools, no compatibility matrices that contradict a version pin, and one job per script — speculative surface must be maintained and will drift.
    14	- **T-94** In the refactor phase, only simplify code that exists; structure added in preparation for a future feature is speculation and gets reverted — YAGNI applies to structure as much as to features.
    15	- **T-95** Read repeated test setup as a message about the production type: fields every spec must supply but none asserts on should stop being required — a test helper that hides the repetition papers over the design signal.
    16	- **T-96** Never probe a data source by instrumenting production code — no debug prints, no temporarily stripped filters; query the source directly with its own tool, read-only, or state the obstacle and ask — instrumenting the implementation corrupts the very suite you are using to judge it and leaves debris in the product.
    17	- **T-97** Never silence a linter (noqa-style markers) to preserve a design; treat the lint pressure as feedback about the design you just introduced.
    18	- **T-99** Introduce a shared test fixture or helper only when at least two existing specs consume it in the same commit, and name those uses as the commit's motivation — two live call sites is the evidence that turns a speculative helper into a justified one.

     1	# Outside-in flow — from story to failing acceptance spec
     2	
     3	The outermost acceptance spec states what the user observes; it stays RED while the feature is in progress and its pull is what drives every inner step. Write it first, then let each failure route you inward.
     4	
     5	- **T-01** Begin every story at the outermost observable boundary its acceptance criteria name (the command invocation, the entry point), watch that spec fail, and let it drive inward to units — never open with a unit spec for a function the criteria do not mention, because the story already states what the user sees and any test above that is a guess about internal structure.
     6	- **T-02** The acceptance spec stays RED until the feature is fully implemented; a red acceptance spec on the main line means feature-in-progress by design. Do not clear it, skip it, or fake it green to tidy the suite — when it passes, that is how you know the feature is complete.
     7	- **T-03** Route a failing acceptance spec inward to a unit spec that names the missing behavior; never go straight from red acceptance to production code, because the acceptance spec states the goal and the unit spec is what drives the design of the piece that closes the gap.
     8	- **T-04** Work one scenario at a time: keep exactly one spec red, and commit the not-yet-worked scenarios as skipped placeholders so the backlog stays visible in `pytest --spec` while the suite stays green — several reds hide which failure you are chasing, and batching scenarios removes each one's individual red-bar signal.
     9	- **T-05** A labeled hardcoded fake is legitimate only while something red still pulls the implementation forward. A fake that turns the outermost RED green owes a unit-driven real implementation in the same sitting, stated in the commit body — and never a meta-test that detects the fake, because once nothing is red the next test you write can only police the fake instead of specifying behavior.
    10	- **T-06** Walking-skeleton exemption: while the skeleton is being stood up, ceremony is relaxed — prefer the smallest change that restores the feedback loop over a full cycle per step, and say explicitly that you are doing so, because process theatre that delays the skeleton defeats the purpose the process exists to serve.
    11	- **T-07** Slice by testability: when a defect or behavior sits at the intersection of two stories, schedule it with the story whose scenarios make it falsifiable and record that decision in the backlog — fixing it now means writing a fix with no scenario that can catch it going wrong.
    12	- **T-08** Before implementing from domain research, validate the research against every story in the backlog column and state, per story, the concrete predicate that satisfies its acceptance criteria — research that only explains the current failing spec does not cover the feature.
    13	- **T-09** Confirm a domain hypothesis against the real data source before writing it into a story card, a filter, or a spec, and state explicitly when your evidence set cannot falsify it — fixtures are constructions that can only confirm what was built into them. Enumerate the complete candidate set before generalizing, because two agreeing observations are not a mapping; the disconfirming case is the one that decides the rule.

     1	# Writing a spec — names, structure, docstrings
     2	
     3	The describe_/it_ sentence is the requirements document: `pytest --spec` renders these names as living documentation for humans, so every naming choice is a documentation edit.
     4	
     5	- **T-35** Name spec files `<module_name>_spec.py` — the BDD convention makes the file's subject legible from the filename.
     6	- **T-36** `describe_` names the feature or command under test; `it_` names the behavior — the pair reads as prose (e.g. `describe_app_list_with_filter` / `it_filters_by_status`, so spec output reads as the backlog). Never name a spec for the mechanism it exercises — "attempts to", "database", "mock", or any implementation noun in a spec name is a rewrite request, because a mechanism name documents how the code happens to work today, not the requirement. Rename any describe block whose name mentions something the block does not constrain, including the story that merely motivated its fixtures — an inaccurate name corrupts the documentation.
     7	- **T-37** Keep the spec tree at most two levels with one `describe_` per function or command; never add a nesting level that carries no information, and never interleave one function's specs inside another's block — it makes the living documentation illegible.
     8	- **T-38** Docstrings are for pending specs only: the story's when/then lives as a docstring while the spec is `@pytest.mark.skip`, and the docstring is deleted in the same commit that implements the body — but only once every clause of the scenario has a corresponding assertion, because until then the docstring is the only evidence the spec is incomplete (find a clause with no assertion: add the assertion, never delete the clause). Never keep a docstring on an implemented spec — the name and assertions ARE the specification, and the prose copy is the one that rots. Never apply a docstring policy as a blanket sweep in either direction.
     9	- **T-39** A placeholder spec gets `@pytest.mark.skip`, never a bare `pass` body — a pass body renders as a passing tick, so the living documentation claims a behavior nothing verifies. Never discharge a TDD obligation with a body that is only `pytest.skip(...)` either — a test that can never fail is a comment with a runtime cost; if the behavior cannot be expressed falsifiably yet, it stays in the backlog.
    10	- **T-40** Land a new spec in two moves: first the describe/it names carrying the scenario as docstring under a skip marker, then the executable body — naming the behavior is a decision the pair reviews before any assertion commits you to a mechanism.
    11	- **T-41** No comments in specs that restate what the code says; put the explanation of an assertion in its failure message — a comment is invisible when the test fails, and the message is what the next reader actually sees.
    12	- **T-42** Import the module under test once at the top of the spec file — per-test imports are noise that hides which module the file is about.
    13	- **T-43** Order the it_ cases inside a describe block by rising complexity, and size collection specs 0, 1, n — the file is read top-down as documentation, and 0-1-many is the minimal set that exercises collection logic.
    14	- **T-44** One it_ asserts one behavior — a bundled test cannot tell you which behavior broke, and it lets an implementation satisfy several claims by accident.
    15	- **T-45** Do not add type annotations to spec functions — they add no value on it_ bodies and only generate gate friction.
    16	- **T-46** If a spec must address a helper directly, make the helper public and rename it in the same edit (and re-privatize it if the reason later evaporates) — a test reaching into a leading-underscore name declares the name public by fact while the code still claims it is not.
    17	- **T-47** Reject a proposed scenario unless you can name the distinct failure path it exercises and a realistic environment that produces it, and do not spec language artifacts the domain cannot produce — a spec for an unreachable case adds a maintenance obligation without constraining any requirement.
    18	- **T-48** When converting or restyling existing specs, refactor them in place, in the same file, under the same names — never a parallel spec file or duplicate suite, because two suites specifying one behavior will disagree and then neither is authoritative.
    19	- **T-49** Never replace a spec file wholesale: read it, then produce a diff that only adds or refines, with every pre-existing spec surviving — the suite is the executable contract, so deleting a spec silently deletes a requirement.
