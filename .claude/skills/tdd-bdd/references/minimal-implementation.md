# Minimal implementation, YAGNI, and coverage

Code is a liability: every line must have been demanded by a failing spec, and an uncovered line is evidence of code nothing demanded — the fix is removing the code or specifying the behavior, never a test written to execute the line.

- **T-85** No implementation without a failing spec that demanded it; if implementation was edited ahead of a spec, revert it to the pre-edit state before proposing anything — without a spec pulling against it, the change is editorial fiat, and there was no moment at which a failing test drove the behavior into existence.
- **T-86** Write no defensive code that no spec demanded — no existence guards, no blanket exception handlers that print and return an empty default, no fallbacks added for "consistency" or "to be safe" — untested defensive code is unspecified behavior that can be wrong invisibly, and a silent guard can BE the bug. When you find one already written, delete it rather than adding a test to cover it — a test written after reading the implementation can only ratify it.
- **T-87** Before adding any guard or conversion, demonstrate the case occurs: query the real data source and report the counts, or execute the path and observe the actual exception type; if the case cannot occur, delete the guard and narrow the type signature instead — and check the query that produced the data, because a case the query already excludes is dead code in the guard that merely suggests to the reader that it could occur.
- **T-88** An uncovered line is evidence that code exists which no requirement asked for: trace its provenance (git log -S, git blame) and ask whether any spec ever demanded it, then take one of the two exits the investigation opens — delete the line if it is defensive residue no requirement demanded, or write the missing spec if it names a real behavior nobody specified. The forbidden third option is a test whose stated purpose is to execute the flagged line, because that inverts the discipline the metric is supposed to measure.
- **T-89** Coverage is a diagnostic residue of good specs, never a target: never retrofit tests to raise the number, and never dismiss a gap as "defensive programming not worth testing" without first checking reachability and provenance — both moves were wrong every time they were tried.
- **T-90** Never justify deleting a spec by "coverage stayed flat": coverage measures line execution, not contract specification, so a boundary-contract spec can be unique while contributing zero coverage; prove redundancy by showing a code mutation the remaining specs still catch — and after restoring a doubted spec, introduce the bug it claims to catch, watch it fail, and revert.
- **T-91** When a production change breaks an existing spec, repair the spec or revert the change; never add a skip marker to restore green — skipping converts a failing requirement into an invisible one. A skipped spec may hold a place for a scenario not yet started, never stand in for a behavior already implemented — a skip committed next to shipped production code is an unspecified requirement wearing a test's name.
- **T-92** Delete any capability the current fixtures cannot falsify — untestable-now is the YAGNI detector: a parameter, branch, and test that no fixture can exercise are all decoration.
- **T-93** Create only the directories and files a current spec demands and delete speculative scaffolding as soon as it is noticed; apply YAGNI to docs and tooling exactly as to code — no documentation for unadopted tools, no compatibility matrices that contradict a version pin, and one job per script — speculative surface must be maintained and will drift.
- **T-94** In the refactor phase, only simplify code that exists; structure added in preparation for a future feature is speculation and gets reverted — YAGNI applies to structure as much as to features.
- **T-95** Read repeated test setup as a message about the production type: fields every spec must supply but none asserts on should stop being required — a test helper that hides the repetition papers over the design signal. Before relaxing the type, trace why the field was required — git blame the declaration and find its current consumers (T-23) — because the repetition is evidence about the design, not yet a verdict on it.
- **T-96** Never probe a data source by instrumenting production code — no debug prints, no temporarily stripped filters; query the source directly with its own tool, read-only, or state the obstacle and ask — instrumenting the implementation corrupts the very suite you are using to judge it and leaves debris in the product.
- **T-97** Never silence a linter (noqa-style markers) to preserve a design; treat the lint pressure as feedback about the design you just introduced.
- **T-99** Introduce a shared pytest fixture or cross-spec helper only when at least two specs consume it in the same commit, and name those uses as the commit's motivation — two live call sites is the evidence that turns a speculative helper into a justified one; anticipated future conversions are not call sites. A data builder landed together with the specs that consume it is not a shared helper and not speculative — the stub-helper pattern (T-81) governs it.
