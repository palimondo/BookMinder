# Writing a spec — names, structure, docstrings

The describe_/it_ sentence is the requirements document: `pytest --spec` renders these names as living documentation for humans, so every naming choice is a documentation edit.

- **T-35** Name spec files `<module_name>_spec.py` — the BDD convention makes the file's subject legible from the filename.
- **T-36** `describe_` names the feature or command under test; `it_` names the behavior — the pair reads as prose (e.g. `describe_app_list_with_filter` / `it_filters_by_status`, so spec output reads as the backlog). Never name a spec for the mechanism it exercises — "attempts to", "database", "mock", or any implementation noun in a spec name is a rewrite request, because a mechanism name documents how the code happens to work today, not the requirement. Rename any describe block whose name mentions something the block does not constrain, including the story that merely motivated its fixtures — an inaccurate name corrupts the documentation.
- **T-37** Keep the spec tree at most two levels with one `describe_` per function or command; never add a nesting level that carries no information, and never interleave one function's specs inside another's block — it makes the living documentation illegible.
- **T-38** Docstrings are for pending specs only: the story's when/then lives as a docstring while the spec is `@pytest.mark.skip`, and the docstring is deleted in the same commit that implements the body — but only once every clause of the scenario has a corresponding assertion, because until then the docstring is the only evidence the spec is incomplete (find a clause with no assertion: add the assertion, never delete the clause). Never keep a docstring on an implemented spec — the name and assertions ARE the specification, and the prose copy is the one that rots. Never apply a docstring policy as a blanket sweep in either direction.
- **T-39** A placeholder spec gets `@pytest.mark.skip`, never a bare `pass` body — a pass body renders as a passing tick, so the living documentation claims a behavior nothing verifies. Never discharge a TDD obligation with a body that is only `pytest.skip(...)` either — a test that can never fail is a comment with a runtime cost; if the behavior cannot be expressed falsifiably yet, it stays in the backlog.
- **T-40** Land a new spec in two moves: first the describe/it names carrying the scenario as docstring under a skip marker, then the executable body — naming the behavior is a decision the pair reviews before any assertion commits you to a mechanism.
- **T-41** No comments in specs that restate what the code says; put the explanation of an assertion in its failure message — a comment is invisible when the test fails, and the message is what the next reader actually sees.
- **T-42** Import the module under test once at the top of the spec file — per-test imports are noise that hides which module the file is about.
- **T-43** Order the it_ cases inside a describe block by rising complexity, and size collection specs 0, 1, n — the file is read top-down as documentation, and 0-1-many is the minimal set that exercises collection logic.
- **T-44** One it_ asserts one behavior — a bundled test cannot tell you which behavior broke, and it lets an implementation satisfy several claims by accident.
- **T-45** Do not add type annotations to spec functions — they add no value on it_ bodies and only generate gate friction; when the type checker demands them, exclude the spec tree from type checking rather than annotating specs to satisfy it, while leaving lint and format applied to specs.
- **T-46** If a spec must address a helper directly, make the helper public and rename it in the same edit (and re-privatize it if the reason later evaporates) — a test reaching into a leading-underscore name declares the name public by fact while the code still claims it is not.
- **T-47** Reject a proposed scenario unless you can name the distinct failure path it exercises and a realistic environment that produces it, and do not spec language artifacts the domain cannot produce — a spec for an unreachable case adds a maintenance obligation without constraining any requirement.
- **T-48** When converting or restyling existing specs, refactor them in place, in the same file, under the same names — never a parallel spec file or duplicate suite, because two suites specifying one behavior will disagree and then neither is authoritative.
- **T-49** Never replace a spec file wholesale: read it, then produce a diff that only adds or refines, with every pre-existing spec surviving — the suite is the executable contract, so deleting a spec silently deletes a requirement.
