# Assertion integrity — pin the requirement, nothing else

An assertion is a falsifiable claim about a requirement. Calibrate both ways: maximal constraint on what the requirement names, zero constraint on what it does not.

- **T-50** Express the minimal constraint that still falsifies — fewest fields, fewest assertions; one positive example suffices, so do not enumerate negative cases by name alongside it — express the negative as absence of the property under a non-emptiness guard (T-59), because extra named examples add maintenance surface without adding constraint.
- **T-51** Before calling a spec meaningful, check whether it would still pass against a stub returning an empty collection, and guard every loop or conditional assertion with a non-emptiness assertion — type checks plus `if x:` are satisfied by a function that does nothing, so the spec certifies the stub instead of the requirement.
- **T-52** Assert exact identity sets where membership IS the requirement (the census is known, so anything weaker throws information away); never encode a behavioral contract — a limit, a cap, a recency window — via fixture cardinality, because a count pins nothing the requirement names and breaks when the fixture grows. Test limit properties at the layer that controls volume.
- **T-53** Never weaken an assertion to make it pass against the fixture you happen to have, and never repair an unconditionally-true assertion by hardcoding a fixture-derived number. When the property you want to pin is not this layer's to pin, say which layer owns it and leave the spec asserting only what this layer can falsify — a limit belongs to whichever spec controls the volume, not to a count copied out of the fixture.
- **T-54** When a fixture-backed assertion fails, decide whether the named datum is the requirement or incidental: if it is the requirement, fix the fixture to contain it by copying the real record in (T-76), never by authoring one — rewriting the expectation to match the data destroys the requirement the spec encoded; if it is incidental, correct the expected value to what the fixture actually contains. Either way keep the assertion at full strength — a relaxed assertion turns a discovered mismatch into a permanently unfalsifiable claim.
- **T-55** When production output changes and a spec fails, decide and state which of the two is wrong before editing either — an assertion rewritten to match observed output stops being a specification and becomes a transcript of current behavior. Never change an asserted literal under an unchanged it_ name: if the specified behavior changed, the name changes with it, because otherwise a different contract hides under the same sentence in the living documentation.
- **T-56** Before rewriting or replacing an existing spec, recover why it exists — trace the construct's history (git log -S) and read the change that introduced it — then enumerate the properties it constrains and show the replacement constrains each one; if it does not, say so instead of proposing the edit — replacements silently drop contracts under unchanged names, and a construct whose motivation you have not recovered is not yours to replace.
- **T-57** Never write a disjunctive assertion — a test that passes under two contradictory outcomes asserts nothing and can never go red for the right reason.
- **T-58** Assert the presence of correct behavior, never the absence of a specific wrong implementation — negative space is unbounded, the assertion cannot fail for the right reason, and it becomes a historical artifact the moment the wrong implementation is gone.
- **T-59** Prefer the assertion that names the property over one that hardcodes incidental content, paired with a non-emptiness guard — pinning a particular datum couples the spec to fixture churn rather than to the behavior. Never write an assertion whose expected value is an accident of the current fixture (e.g. encoding a fixture's emptiness) — it passes without the feature existing; if the fixture cannot exhibit the behavior, fix the fixture first, by copying from the real source (T-76). Before asserting on specific data, run the product against the fixture and read the actual output — an assertion carried over from an older fixture, or copied from a neighbouring spec, names data the fixture no longer contains; when you find one, grep the tree and fix the story cards and docs that carry the same stale datum.
- **T-60** On an error-path spec, assert both the user-facing message and a fragment unique to the path under test (a discriminating message or path fragment) — a message shared by several failure paths stays green for the wrong reason indefinitely, and the discriminating fragment is what converts "an error happened" into a falsifiable claim about which error happened. Keep both assertions: they specify different requirements — what the user is told, and which internal path produced it.
- **T-61** Do not pin what the requirement does not own: no absolute machine paths or full internal message text in acceptance assertions — every unrelated wording or path change then breaks the spec for reasons unrelated to the behavior it names. In a boundary spec, assert the sentinel your own double injected, never the real wording or path the layer below produces — verifying pass-through (T-70) and coupling to a lower layer's internals are different claims.
- **T-62** Delete a spec that a stronger spec already subsumes, and when two specs constrain the same behavior with equal strength, keep the one whose motivation you can state; then sweep the file for other instances of the same redundancy — whole-output equality already pins ordering, content, and absence, so the weaker check adds maintenance without falsifying power, and redundancy comes in clusters.
- **T-63** Configure nothing on a mock that the test does not later assert on — an unused return value implies the test cares about something it never checks. In a coordination spec, assert the exact call sequence (call_args_list): it subsumes the count, and output assertions belong to the collaborator's own spec.
- **T-64** If a mock makes an argument irrelevant, the spec does not constrain that argument — fix the seam; do not relabel the argument as a dummy to make the vacuity tidy, because documenting that a test proves nothing is not the same as making it prove something.
- **T-65** A green counts as evidence only if you can name what would have made it red: after installing a test seam, prove the seam took effect (item counts, run time, the path actually read) before treating the pass as a result — an inert seam leaves the suite green against the wrong data, proving nothing.
