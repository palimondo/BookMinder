# Outside-in flow — from story to failing acceptance spec

The outermost acceptance spec states what the user observes; it stays RED while the feature is in progress and its pull is what drives every inner step. Write it first, then let each failure route you inward.

- **T-01** Begin every story at the outermost observable boundary its acceptance criteria name (the command invocation, the entry point), watch that spec fail, and let it drive inward to units — never open with a unit spec for a function the criteria do not mention, because the story already states what the user sees and any test above that is a guess about internal structure.
- **T-02** The acceptance spec stays RED until the feature is fully implemented; a red acceptance spec on the main line means feature-in-progress by design. Do not clear it, skip it, or fake it green to tidy the suite — when it passes, that is how you know the feature is complete.
- **T-03** Route a failing acceptance spec inward to a unit spec that names the missing behavior; never go straight from red acceptance to production code, because the acceptance spec states the goal and the unit spec is what drives the design of the piece that closes the gap.
- **T-04** Work one scenario at a time: keep exactly one spec red, and commit the not-yet-worked scenarios as skipped placeholders so the backlog stays visible in `pytest --spec` while the suite stays green — several reds hide which failure you are chasing, and batching scenarios removes each one's individual red-bar signal.
- **T-05** A labeled hardcoded fake is legitimate only while something red still pulls the implementation forward. A fake that turns the outermost RED green owes a unit-driven real implementation in the same sitting, stated in the commit body — and never a meta-test that detects the fake, because once nothing is red the next test you write can only police the fake instead of specifying behavior.
- **T-06** Walking-skeleton exemption: while the skeleton is being stood up, ceremony is relaxed — prefer the smallest change that restores the feedback loop over a full cycle per step, and say explicitly that you are doing so, because process theatre that delays the skeleton defeats the purpose the process exists to serve.
- **T-07** Slice by testability: when a defect or behavior sits at the intersection of two stories, schedule it with the story whose scenarios make it falsifiable and record that decision in the backlog — fixing it now means writing a fix with no scenario that can catch it going wrong.
- **T-08** Before implementing from domain research, validate the research against every story in the backlog column and state, per story, the concrete predicate that satisfies its acceptance criteria — research that only explains the current failing spec does not cover the feature.
- **T-09** Confirm a domain hypothesis against the real data source before writing it into a story card, a filter, or a spec, and state explicitly when your evidence set cannot falsify it — fixtures are constructions that can only confirm what was built into them. Enumerate the complete candidate set before generalizing, because two agreeing observations are not a mapping; the disconfirming case is the one that decides the rule.
