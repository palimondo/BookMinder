# Apple Books domain lore

Verification status is honest here: **verified@tree** = encoded in the current code/fixtures and exercised by the suite; **observed-2025** = established against a live library in 2025, needs a fresh live-DB probe before you lean on it; **hypothesis** = open, never settled. This environment has no live Apple Books database — nothing here can be re-verified in place, only against fixtures.

## Data sources

- **B-40 — Two sandboxed containers (verified@tree, encoded at library.py:17-25).** `~/Library/Containers/com.apple.BKAgentService/Data/Documents/iBooks/Books/` holds `Books.plist` (the catalogue) beside per-book `<numeric-id>.epub` items. `~/Library/Containers/com.apple.iBooksX/Data/Documents/BKLibrary/` holds the library database. Discover the database by glob — `BKLibrary-*.sqlite` — never by literal filename: the numeric segments (e.g. `BKLibrary-1-091020131601.sqlite`) are per-install artifacts.
- **B-41 — Plist vs database roles (observed-2025; the split is load-bearing for the whole design).** `Books.plist` is a catalogue: `itemName`, `artistName`, `path`, `updateDate`. Its `BKPercentComplete` appears only on finished books (always 1.0) — it cannot express in-progress reading. Real reading state lives in the database table `ZBKLIBRARYASSET` (`ZREADINGPROGRESS`, `ZLASTOPENDATE`, `ZISFINISHED`, `ZDATEFINISHED`, `ZCREATIONDATE`). The database is the authoritative catalogue: titles the database knew were demonstrably missing from the plist even after a fresh `plutil -convert swift` snapshot, and the cause was never established (the author's verdict: still a mystery) — so absence from the plist proves nothing in either direction, neither about library membership nor about cloud status. `updateDate` in the plist is probably publisher-revision metadata rather than reading activity — the author's hypothesis, never verified; what the episode actually settled is that the `sort_by='updated'` feature was deleted as YAGNI precisely because the field's meaning was unknown. BookMinder cares about the user's relationship to the book, which lives in the database. Books lazy-download from iCloud: a book in the catalogue with no file on disk is a valid library entry — never filter books by on-disk file existence.
- **B-42 — Apple epoch (verified@tree, library.py:11,65-66).** Core Data timestamps count seconds from 2001-01-01 UTC, not 1970 — raw values look like plausible Unix times and are silently ~31 years wrong without the `APPLE_EPOCH` offset.

## The ZSTATE census — the project's signature reflex

- **B-43 — ZSTATE is a small enum whose census must be re-taken, not recalled.** Single-value stories about ZSTATE ("5 means cloud", "3 is the only cloud value") kept being revised by the next batch of real rows; books showing the UI cloud icon were observed at ZSTATE 1, 3, and 6. The working set the code encodes (observed-2025, at library.py:76-77): **1** = present locally (including downloaded samples), **3** = cloud book, **6** = cloud sample not yet downloaded. **ZSTATE 5 is an OPEN HYPOTHESIS, not a verified mapping.** Two observations exist — in this order — and they are consistent with each other without settling it: a batch census first showed 5 only as a *second* row for a title that already had a 3; a later, more systematic `ZSERIESID` join on one series then showed 5 carried both by the series entity (whose ZTITLE was the series name, ZAUTHOR "MultipleAuthors") and by the unowned member titles sharing the owned book's series id — a structure that would also produce exactly that second row. The author's own framing left the entity/member relation unknown, and the ZSTATE-5 population is large (~206 rows, dominated by store collections and public-domain classics). `docs/apple_books.md` records "Series Entity / Unowned Series Book" under a "Verified ZSTATE Mappings" heading and over-claims: the ZTITLE-based entity/member discriminator written there was the agent's own substitute after the author rejected a ZAUTHOR heuristic and pointed at the entry/seriesid structure instead. Treat 5 as unmapped until a live-DB re-census. The method that produced the ZSERIESID breakthrough — the author's directive to enumerate all distinct values DB-first and characterize each, instead of reasoning UI-first from the values already seen — is this page's standing reflex.
- **B-44 — Sample detection is a composite predicate (verified@tree, library.py:77).** `is_sample` = `ZSTATE = 6 OR ZISSAMPLE = 1`. `ZISSAMPLE = 0` is never proof a book is not a sample — unmistakable UI samples carried `ZISSAMPLE = 0` and were identifiable only by `ZSTATE = 6`. Lifecycle (hypothesis; reconstructed second-hand in a log analysis the author relayed, never probed live before/after): a store sample enters the library as `ZSTATE=6, ZISSAMPLE=0` (cloud sample) and becomes `ZSTATE=1, ZISSAMPLE=1` once opened/downloaded. ZSTATE 6 is the common case, downloaded samples the edge case — cover both. Per-title values are time-varying, not stable facts: the same title read `ZSTATE=6, ZISSAMPLE=0` in one probe and `ZSTATE=1, ZISSAMPLE=1` after being opened — the lifecycle above is the proposed mechanism, not noise — so any per-title claim needs a freshness stamp and a re-run query, never a citation of notes. Cloud display vs cloud filter diverge at HEAD (verified@tree): `is_cloud` = `ZSTATE in (3, 6)` (library.py:76) but `--filter cloud` matches `ZSTATE = 3` only (library.py:154-159) — a cloud sample displays ☁️ yet is excluded by the cloud filter. The 3-only filter is where the author's revert of an unauthorized widening left it: he pulled a 3-or-6 change back because it landed before he approved it, not because the wider predicate was ruled wrong — so do not change either side without his direction and a spec.
- **B-45 — ZCONTENTTYPE is unverified (hypothesis).** Likely 1 = book (EPUB), 3 = PDF — hedged until re-verified on a live database. `docs/apple_books.md` states it hedged at line 60 and flat at lines 114-115; the hedged form governs.
- **B-46 — Column facts.** `ZTITLE` is not a key (observed-2025): one title can have multiple rows (duplicate rows at different ZSTATEs, even under two author strings), so any title lookup must handle and explain duplicates or detection becomes non-deterministic. `ZISFINISHED = 1` is the sole definition of finished (observed-2025): finished books exist below 100% progress, so never require `ZREADINGPROGRESS = 1.0`. `ZLASTOPENDATE` was never NULL for rows with progress > 0 (observed-2025, 221 rows, 0 nulls) — the basis for not guarding it; re-verify before adding or removing guards.
- **B-47 — Samples and `list recent` (hypothesis).** Apple Books appears never to populate `ZREADINGPROGRESS` for samples — a sample's reading position was traced to a type-3 annotation in the AEAnnotation database instead. Both claims are second-hand: a log-analysis summary the author relayed plus the agent's own requirements reasoning, never a live probe. Counter-observation from the same session: the UI renders some cloud samples at 1% (B-53 records that as an Apple UI quirk not to be replicated); what remains untested is the database-side claim that `ZREADINGPROGRESS` stays 0.0 for samples. Since `list recent` filters on `ZREADINGPROGRESS > 0`, sample filtering there is structurally near-empty; library-wide sample listing belongs on `list all`.
- **B-48 — "Want to Read" is unresolved (hypothesis).** Composition held as unread-or-sample (`ZREADINGPROGRESS = 0` and not finished, OR sample) for all observed titles, but its ordering was never established — the recorded ZCREATIONDATE conclusion rests on a known arithmetic error. The list is computed by Apple, not marked by the user: document observed database behavior, never inferred user intent, and say "unknown" when the mechanism is unknown.

## Environment facts

- **B-49 — Container lifecycle (observed-2025 on real machines).** `com.apple.iBooksX` is created at macOS account setup; `com.apple.BKAgentService`, `Books.plist`, and the `BKLibrary-*.sqlite` (with 0 rows) are all created together on first launch of Apple Books — no Apple ID required. Reading another user's `~/Library` requires sudo; a plain `--user <name>` run fails with PermissionError. These states are exactly what the fixture personas encode.
- **B-50 — Plist mechanics.** `Books.plist` stores `Books` as an ARRAY of dicts — a dict-keyed-by-id variant parses without error and silently yields zero books (verified@tree: the code guards for list shape, library.py:85-86). Read with `plistlib.load(open(path, "rb"))` — it auto-detects binary and XML; never shell out to `plutil -convert`. For human/agent exploration, render plists as Swift literals: `plutil -convert swift -o out.swift Books.plist` — far more token-efficient than XML; that is what the `All_Books*.swift` dumps are.
- **B-51 — Path correlation is an open problem.** `_row_to_book` sets `path=""` pending a `ZASSETID`-keyed correlation with `Books.plist` (verified@tree, library.py:73; `path` is `NotRequired` on `Book` for the same reason). Whether the database has any usable path column was never actually checked — the question was left as an acknowledged TODO at the author's direction — so "the path exists only in Books.plist" is a needs-live-DB guess, not an established schema fact. This is acknowledged design debt, not an oversight.

## Working the database

- **B-52 — Query discipline.** Answer one-off questions with the `sqlite3` CLI directly — no throwaway .py scripts in the tree, no print-debugging through production code. Use targeted column lists, never `SELECT *` (blurb columns flood the context). Parameterize titles with `?` placeholders — hand-escaping apostrophes ("What's Our Problem?") fails repeatedly. When a diacritics-bearing title returns nothing, retry `LIKE` on the longest ASCII-only prefix before concluding the row is absent — the shell round-trip, not the database, is what fails. When probing N items with the same shape, batch with `IN (...)`.
- **B-53 — docs/apple_books.md epistemic status.** It is the captured output of the reverse-engineering phase — a running record of guesses about a schema Apple does not document; its "Edge Cases" and NULL-handling sections, like its `ZCONTENTTYPE` mapping (B-45), are speculation written in the same voice as its observations. It is the thing under test, never the reference: verify any attribute row-by-row against the UI screenshots in `docs/ui/apple/` and a live query, never against the doc's own prose. Editing rules the author enforces: the doc stays descriptive of storage (no SQL that prescribes a feature's filtering strategy); every SQL query lives in the single Database-to-UI-Mapping section other sections link to (two copies of one query is how it contradicted itself); UI quirks (cloud samples rendered "1%") are documented but never replicated in the implementation; screenshots are committed into docs/ and referenced inline next to the claims they support, each labelled with the platform that produced it (iPhone tiles and macOS list views use different attribute vocabularies — macOS "Complete" is a long-form percentage, not a status); preserve the section's existing segmentation when updating contents.
