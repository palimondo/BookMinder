# Apple Books domain

The compressed record of what the project learned about Apple Books storage on macOS — the facts BookMinder's code and specs rest on, stated so an agent can write correct code without opening `docs/apple_books.md`. The doc is the territory map from the research spike, with evidence, screenshots, and the discovery narrative; this page points into it by section name only where depth or evidence lives beyond the fact. What a spec pins against the fixtures is established; the rest is recorded observation, and what was never established is stated as unknown.

## Data sources

- **B-40 — Two containers, one glob.** Under `~/Library/Containers/`, `com.apple.BKAgentService/Data/Documents/iBooks/Books/` holds `Books.plist` beside the per-book `<asset-id>.epub` files, and `com.apple.iBooksX/Data/Documents/BKLibrary/` holds the library database. The database file name carries per-install numeric segments, so `library.py` finds it by glob (`BKLibrary-*.sqlite`, first match) — never by literal name. Depth: doc, "Container Directories" and "Data Sources".
- **B-41 — Books.plist is the catalogue, the database is the reading state.** Each entry in the plist's `Books` list carries `itemName`, `artistName`, `path` (the only file path the code reads), and `updateDate`; `BKPercentComplete` appears only on finished books, always 1.0, so the plist cannot express progress. Reading state — `ZREADINGPROGRESS` (0.0 to 1.0), `ZLASTOPENDATE`, `ZISFINISHED`, `ZDATEFINISHED`, `ZCREATIONDATE` — lives in the database table `ZBKLIBRARYASSET`, which is also the authoritative catalogue: titles the database knew were missing from the plist even in a fresh snapshot, for a reason never established, so absence from the plist proves nothing about membership or cloud status. BookMinder cares about the user's relationship to the book, so the list commands read the database. Depth: doc, "Data Sources" and "Progress Data Sources Hierarchy".
- **B-42 — `updateDate` means something unknown.** Probably the publisher's revision date, not reading activity; never verified. The consequence was a decision: the `sort_by='updated'` feature was deleted as YAGNI because sorting on a field of unknown meaning is not a feature. Recency comes from `ZLASTOPENDATE`.
- **B-43 — Never filter by on-disk file existence.** Books lazy-download from iCloud: a library entry with no `.epub` on disk is a valid, normal entry. Presence on disk is a download state, not a membership test; no code path stats a book file.
- **B-44 — Apple epoch.** Database timestamps count seconds from 2001-01-01 UTC, not 1970; raw values look like plausible Unix times and are silently about 31 years wrong. `library.py` converts with `APPLE_EPOCH + timedelta(seconds=value)`. Detail: doc, "Apple Timestamp Format Details".

## The library table and its columns

- **B-45 — ZSTATE.** A small integer enum. The mapping the code encodes: 1 = present locally (downloaded books and downloaded samples), 3 = cloud book, 6 = cloud sample not yet downloaded; the fixture's cloud rows carry NULL `ZKIND` and `ZPATH`. ZSTATE 5 is unmapped: a `ZSERIESID` join from an owned book returned 5 on the series entity row and on unowned member titles sharing the series id, no criterion for telling those apart was established, and the population is large. Which values show a cloud icon is unsettled too: cloud-icon books were seen at 1, 3, and 6, but that observation crossed devices (iPhone UI against the Mac's database, where one title can legitimately differ), so 1 may mean local-on-the-queried-machine. When a census is taken, enumerate all distinct values DB-first and characterize each — never reason UI-first from values already seen. Evidence: doc, "Observed ZSTATE Mappings" under Domain Language, and "Series Collections".
- **B-46 — Sample detection is a composite predicate.** `is_sample` = `ZSTATE = 6 OR ZISSAMPLE = 1`; the specs pin both halves. `ZISSAMPLE = 0` proves nothing: unmistakable UI samples carried 0 and were identifiable only by ZSTATE 6. The proposed lifecycle — a store sample enters as 6/0 and becomes 1/1 once opened or downloaded — was never observed on one row before and after; it is inferred from one title flipping between queries. Per-title ZSTATE/ZISSAMPLE values are point-in-time: re-run the query, never quote a title from notes. Depth: doc, "Sample Book Handling".
- **B-47 — Cloud display and the cloud filter disagree, by ruling.** `is_cloud` = `ZSTATE in (3, 6)`, so a cloud sample renders with the cloud glyph, but `--filter cloud` on `list recent` matches `ZSTATE = 3` only and `!cloud` matches `ZSTATE != 3` — a cloud sample displays as cloud yet is excluded by the cloud filter. The specs pin only that filtered rows are cloud, not the predicate's width, and the `!cloud` spec holds only because no fixture row sits at ZSTATE 6 with progress. The 3-only filter is where the author's revert of an unauthorized 3-or-6 widening left it — reverted for landing before approval, not because the wider predicate was ruled wrong. Change neither side without his direction and a spec. `list all` accepts the cloud values and applies no cloud predicate at all — the current-state page's B-68.
- **B-48 — ZCONTENTTYPE mapping is unverified.** Likely 1 = book (EPUB), 3 = PDF; every fixture row reads 1, so the fixtures cannot confirm the PDF half and no spec pins either. The doc hedges the mapping in "Content Type Identification" and Domain Language; the hedged form governs.
- **B-49 — ZTITLE is not a key.** One title can occupy several rows — at different ZSTATEs, and once under two author strings for two editions of the same title. A title lookup must handle duplicates explicitly or detection becomes non-deterministic. Evidence: the iPhone screenshot beside the `ZTITLE` field in the doc's "BKLibrary SQLite Database" field list.
- **B-50 — `ZISFINISHED = 1` alone means finished.** Finished books were observed below 100% progress, so never require `ZREADINGPROGRESS = 1.0`; the converse held. The fixture holds no finished book, and its unfinished rows carry NULL, not 0, in `ZISFINISHED` — a not-finished predicate written as `= 0` or `!= 1` matches nothing there. No spec pins this yet; the library spec's finished-book TODO is where it will land. Depth: doc, "Progress Edge Cases".
- **B-51 — `ZLASTOPENDATE` is unguarded.** Never observed NULL on a row with progress above 0, so `_row_to_book` converts it without a NULL guard; the doc's NULL-timestamp warnings under "Timestamp Edge Cases" are speculation, not observations. Add or remove a guard only on live evidence and with a spec.
- **B-52 — Samples and `list recent`.** Samples were never observed with `ZREADINGPROGRESS` above 0.0, and a sample's reading position was traced to a type-3 row in the AEAnnotation database instead; both are second-hand (a relayed log analysis, never a live probe). Since `list recent` filters on `ZREADINGPROGRESS > 0`, its sample filter is structurally near-empty — library-wide sample listing belongs on `list all`, which the specs pin against the fixture's sample titles. Depth: doc, "Sample Book Handling".
- **B-53 — "Want to Read" is computed, not marked.** Apple computes the list; the user flags nothing. Its observed composition is unread-or-sample (`ZREADINGPROGRESS = 0` and not finished, or a sample); its ordering is unknown — the recorded ZCREATIONDATE conclusion rests on a known arithmetic error. Document observed database behavior, never inferred user intent; say "unknown" when the mechanism is unknown. Depth: doc, "Want to Read Section".

## The machine

- **B-54 — Container lifecycle.** `com.apple.iBooksX` is created at macOS account setup; `com.apple.BKAgentService`, `Books.plist`, and an empty-table `BKLibrary-*.sqlite` appear together on the first launch of Apple Books, no Apple ID required; an older install can carry `Books.plist` with no `BKLibrary` directory at all. These are the states the fixture personas encode and the two error messages in `library.py` distinguish (missing directory vs empty directory). Reading another user's `~/Library` requires sudo — a plain `--user <name>` run fails with PermissionError. Depth: doc, "User State Scenarios".
- **B-55 — Plist mechanics.** `Books.plist` stores `Books` as a list of dicts; `library.py` guards for list shape, so a dict-keyed variant parses without error and yields zero books. Read it with `plistlib.load` on a binary-mode handle — it auto-detects binary and XML; never shell out to `plutil -convert` from code. For exploration, render a plist as Swift literals (`plutil -convert swift -o out.swift Books.plist`) — far cheaper in tokens than XML; the untracked `All_Books*.swift` dumps are such renderings.
- **B-56 — Path correlation is open.** `_row_to_book` sets `path=""` pending a `ZASSETID`-keyed correlation with `Books.plist`; `path` is `NotRequired` on `Book` for the same reason. Whether the database carries a usable path column was never checked: the doc lists `ZPATH`, and in the fixture it holds an absolute `.epub` path on two local rows but NULL on the cloud rows and on one downloaded sample, so it is not a reliable path source even there, and no spec pins any of that. Design debt left as a TODO at the author's direction.

## Working the database

- **B-57 — Query discipline.** Answer one-off questions with the `sqlite3` CLI directly — no throwaway scripts in the tree, no print-debugging through production code. Name columns, never `SELECT *` (blurb columns flood the context). Parameterize titles with `?` placeholders — hand-escaping apostrophes fails repeatedly. When a diacritics-bearing title returns nothing, retry `LIKE` on its longest ASCII-only prefix before concluding the row is absent — the shell round-trip, not the database, is what fails. Probe N items of one shape with a single `IN (...)`.

## The doc's standing

- **B-58 — What `docs/apple_books.md` is.** The territory map from the research spike, re-aligned with the project's recorded corrections where the record allowed. Its "Edge Cases and Special Considerations" and "UI Behavior Insights" are guesses written in the observational voice; the rest holds the observations this page compresses. Where this page and the doc differ, this page governs; verify an attribute against a screenshot and a live query, never against the doc's prose alone.
- **B-59 — Editing rules for the doc.** It stays descriptive of storage: no SQL that prescribes a feature's filtering strategy. Every SQL query lives in the single "Database to UI Mapping" section other sections link to — two copies of one query is how the doc contradicted itself. UI quirks (cloud samples rendered "1%") are documented, never replicated. Screenshots are committed under `docs/ui/apple/` and referenced inline beside the claims they support, each labelled with the platform that produced it — iPhone tiles and macOS list views use different attribute vocabularies, and macOS "Complete" is a percentage, not a status. Preserve the existing segmentation when updating contents.
