# Goals and history — what BookMinder is for

## Destination and core question

- **B-01 — Destination.** Build toward an MCP tool for discussing books with Claude: the author reads on his iPhone and wants to talk with an LLM about the book he is reading, its last chapter, and the highlights made since the last conversation. Keep the CLI as the walking skeleton of that vision. The CLI came first deliberately, because the author knows CLI design and TDD/BDD cold while MCP was unfamiliar territory.
- **B-02 — Core question.** Act as the pair programmer in the experiment on whether an LLM can be a good one; the author had no colleagues to pair with, and this project is that experiment. Treat the method as the point: nail verifiable invariants in executable specifications, and treat slicing the problem and designing specs with minimal coupling to implementation as the art, in the London school, GOOS lineage. Derive every process choice from the root principle that the spec's job is nailing requirements in a falsifiable way: executable specification, GOOS layers, enforced layer separation, and delegation contracts all follow from falsifiability, as a hierarchy rather than parallel motivations.
- **B-03 — Why Apple Books as testbed.** Expect the Apple Books database schema to be undocumented and to evolve with each macOS release; the author chose it deliberately for that, so the project tests long-term software evolution and maintenance rather than one-shotting problems the model already knows from pretraining. Verify schema facts against the specs and the domain page rather than assuming the schema you remember.
- **B-04 — Book-grounding motivation (product feeds process).** Treat pretrained simulacra of TDD/BDD experts as shallow caricatures: skewed, non-actionable summaries of real positions. Keep in view a core BookMinder motivation, giving the model access to full books as consultation material, so actionable principles can be extracted from primary sources that did not survive pretraining summarization. Call the failure mode this defeats simulacra-shallowness.
- **B-05 — The project is a vehicle and a benchmark.** Treat the real object of study as whether an AI coding agent can hold a strict ATDD process as a pair programmer. Count as deliverables only the bounded set of process artifacts: the durable chain (story cards expanded into acceptance tests, with working code as the output an agentic system must derive from them), the session diary, and the agent-instruction files (themselves WIP, their techniques untested — his words). Leave AI-written retrospective meta-analysis out of that set and do not produce it: the author calls it slop (see B-31), and every time he affirmed the vehicle framing he qualified it in the same breath, warning the meta-project could turn out to be a big baggage of AI slop in the end. The author (a Product Owner by day job, working in Jeff Patton's User Story Mapping tradition) has long intended the project to double as a benchmark of agentic coding systems.

## History

- **B-06 — BookMind, the predecessor.** Treat BookMind as a working predecessor rather than a failure: it implemented most of the original vision, EPUB parsing, highlight extraction, markdown export, a working CLI, 40 passing tests. The fork to BookMinder was motivated by process, cost, and code quality: the agent took too much unrequested initiative and produced a sprawling codebase at high cost. Never describe BookMind as broken software, and never score BookMinder against BookMind on size, coverage, or feature count: BookMinder is a walking skeleton by explicit request, so the comparison measures the choice, not the outcome. Read `ORIGINAL_VISION.md` as a copy of BookMind's first README (verify with `git show 64dc71b:README.md` in the BookMind repo context), not as a BookMinder-specific document.
- **B-07 — Scope discipline is the founding constraint.** Add no capability the author has not asked for: the scope is the GOOS walking skeleton plus whatever the story cards ask for. BookMinder exists specifically to stop the agent from running ahead with its own creative ideas, and the canonical rules file is the instrument of that constraint.
- **B-08 — Apple-only by design.** Never propose, justify, or advertise a change on cross-platform grounds: Apple Books is the product's entire subject, and CI pins macOS.
- **B-67 — Public by design.** Do not treat pushing project material to this repo as an exposure event, and do not relay automated publication warnings about it: the whole repository is public, and the methodology is deliberately developed in the open, session diaries, mining corpora, eval design, and coordination logs included. Stop and ask only for genuinely new content classes: credentials or tokens, third-party private data, or personal data beyond what the author has already published here.
- **B-09 — Timeline in brief.** Summer 2025: intense development, a gold-standard ATDD era, then a process lapse after commit 6f786cc (features landed without proper ATDD; the repair backlog for this still stands), ending in the author's burnout from holding process discipline for models that knew the process but could not perform it (knowing vs performing is the key distinction). ~1 year dormant. 2026-08: reevaluation sessions on cloud infrastructure with no new feature code: the 2025 session diary was mined into a rules corpus, the spec tree was restored wholesale to its pre-reorg concern-based form, the commit-after-RED experiment was first restored and then retired by the author's ruling (git grammar proved an imperfect proxy for process compliance, which transcript analysis measures directly), the agent-instruction files were unified into one canonical rules file, and this skill was compiled. Treat each of those as settled rather than as a proposal to revisit: do not re-mine the diary, do not reorganize the spec tree into layers, do not reinstate commit-after-RED, do not split the canonical rules file back into several, and extend this skill rather than recompiling it. Work the lapse's repair backlog from where the current-state page says it lives.
- **B-10 — The stickiness law.** When a rule keeps being violated, make the durable fix machinery, because corrections shipped as automation (hooks, validators, CI) stick while corrections shipped as prose only partly stick. The author rates Claude Code hooks the most valuable CC innovation for exactly this reason: enforcement via automation, not prose. Leave open, and do not answer for him, the experiment question of how much harness enforcement discipline requires once skills are in place.
